How this course works

Each lesson lasts 120 minutes and is always split the same way: little explaining, a lot of trying. No lesson is theory only, and no exercise asks for things not yet explained.

There is a single common thread: every language construct is learned because the hand needs it. Variables hold a coordinate, arrays hold 21 points, interfaces say what a point looks like, async functions turn on the webcam. No abstract exercise without a reason.

Lesson 1

The first program: variables and types

What really happens when a program "runs", how you set a value aside, and why TypeScript scolds you before running the code instead of after.

  • By the end the student can: write and run a ten-line program, read a compiler error message and understand which line it refers to

15' The teacher shows the finished hand and then writes the first lines live, making mistakes on purpose
60' Exercises 1.1 → 1.5
15' Quick check · homework

Theory

A program is a list of statements that the computer runs one after the other, from top to bottom. The most useful statement at the start is the one that writes a message: 

console.log("ciao");
console.log("mondo");

Two lines, two messages, in that order. There is no magic: if you swap the lines, the result is swapped too.

A variable is a name given to a value, so you can reuse it. In TypeScript you declare two kinds: 

let punteggio = 0;        // can change later
const nome = "Giulia";    // will never change

punteggio = punteggio + 10;   // ok
nome = "Marco";               // ERROR: const cannot be reassigned
Rule of thumb Always use const, and switch to let only when you notice that the value must change. It is not pedantry: when reading the code, const says "this one won't surprise you".

Every value has a type. The three you need today: string (text, in quotes), number (numbers, whole or with a decimal point) and boolean (only true or false). 

const nome: string = "Giulia";
const eta: number = 17;
const maggiorenne: boolean = false;

That : string is the type annotation: it is the part that does not exist in JavaScript and the reason this language is called TypeScript. You can often leave it out, because the compiler works out the type by itself by looking at the value (we say it infers it): 

const nome = "Giulia";   // TypeScript already knows it is a string
nome.toUpperCase();      // in fact here it suggests the text methods

And what is all this for? To make errors appear while you type, not while the program runs in front of users: 

let eta = 17;
eta = "diciassette";
// Error: Type 'string' is not assignable to type 'number'.
// In plain words: "you said a number goes here, and this is text".
How to show it in class Write the error live and let the line get a red underline. Then hover the mouse over it and read the message aloud, explaining it. Present the error message right away as help: it is the difference between those who learn fast and those who get stuck.

Last piece: joining text and values. With backticks ` you write strings into which you can insert values with ${…}: 

const dita = 5;
console.log(`la mano ha ${dita} dita`);
console.log(`e ${dita * 4} falangi... circa`);

Theory

What it is for. A program that always does the same things in the same order is not very useful. The hand in front of the webcam is sometimes there and sometimes not, the fingers are sometimes raised and sometimes closed: the program must decide. And since the hand has twenty-one points, writing the same line twenty-one times is not a workable option: the program must repeat.

We start with comparison. Comparing two values always produces a boolean, that is true or false: the same type seen last time, but this time we do not write it by hand, the computer calculates it. 

const dita = 5;

console.log(dita === 5);    // true   "is equal to"
console.log(dita !== 5);    // false  "is different from"
console.log(dita > 3);      // true   "greater than"
console.log(dita < 3);      // false  "less than"
console.log(dita >= 5);     // true   "greater than or equal"
console.log(dita <= 4);     // false  "less than or equal"
Three equals signs, not two This language has both == and ===, and they do not do the same thing. Double equals, before comparing, converts the values: for it "5" == 5 is true, even though one is text and the other a number. Triple equals converts nothing: "5" === 5 is false, because they are of different types. Course rule, no exceptions: always use === and !==. Double equals produces bugs you only find when the program is finished.

Comparisons are combined with logical operators. There are three, and you read them aloud like plain English: 

const x = 0.4;

console.log(x >= 0 && x <= 1);   // true   "and" → both must be true
console.log(x < 0 || x > 1);     // false  "or"  → one being true is enough
console.log(!(x < 0));           // true   "not" → flips the result

With a boolean value in hand you can finally choose. The if statement runs a block of code only if the condition is true: 

const dita = 5;

if (dita === 5) {
  console.log("mano aperta");
}

The curly braces enclose the block, that is the lines that belong to that if. With else you say what to do when the condition is false, and with else if you line up several questions. The computer tries them from top to bottom and stops at the first true one: 

const dita = 2;

if (dita === 0) {
  console.log("pugno");
} else if (dita === 5) {
  console.log("mano aperta");
} else if (dita === 2) {
  console.log("vittoria");
} else {
  console.log("gesto non riconosciuto");
}

// prints: vittoria
The last else is not mandatory But it is almost always worth adding. It is the "I don't know what this is" branch: without it, when no condition is true the program prints nothing and you are left wondering whether it broke. In the final project that branch really exists: when the recognizer does not understand the gesture, it answers "None", and the application shows a generic hand.

Now on to repeating. The most classic way is the for loop. Written all at once it looks scary, so read it one piece at a time: 

for (let i = 0; i < 5; i++) {
  console.log(i);
}

// prints: 0 1 2 3 4

Inside the round brackets there are three things separated by semicolons, and each has a job:

  1. let i = 0 — the starting point. You create a variable, usually called i (for index), set to zero.
  2. i < 5 — the condition to keep going. Before every round the computer checks it: if true it does the round, if false it leaves the loop.
  3. i++ — what to do at the end of every round. i++ is the short form of i = i + 1.

So the computer runs: i is 0, 0 is less than 5, print, i becomes 1… until i is 5, which is not less than 5, and the loop ends. The body ran five times, with i equal to 0, 1, 2, 3, 4.

The infinite loop If the condition never becomes false — for instance because you forgot i++ — the loop never ends and the browser tab freezes. It is not serious: close the tab and reopen the Playground, which keeps the code in the address. But it will happen to someone, so say it beforehand.

Now you need something to repeat over. An array is an ordered list of values, all of the same type. It is written in square brackets, and its type is the type of the elements followed by []: 

const numeri: number[] = [10, 20, 30, 40];
const nomi: string[] = ["pollice", "indice", "medio"];

console.log(numeri.length);   // 4   → how many elements there are
console.log(numeri[0]);       // 10  → the FIRST element
console.log(numeri[3]);       // 40  → the last one
console.log(numeri[4]);       // undefined → does not exist

Two things must be learned right away, because they cause half of beginners' errors. First: indices start from zero. An array of four elements has indices 0, 1, 2, 3. Second: as a consequence the last index is length - 1, never length.

Out of bounds: undefined If you ask for an element that is not there, the program does not get angry: it returns undefined, the special value "nothing here". In the Playground TypeScript tells you that numeri[4] is a number and does not complain: it trusts that you know how long the array is. Then, at run time, out pops undefined and the arithmetic gives NaN (Not a Number). If you see NaN printed on screen, nine times out of ten you read past the end of an array.

Putting loop and array together gives the most used line of the whole course:

const numeri: number[] = [10, 20, 30, 40];

for (let i = 0; i < numeri.length; i++) {
  console.log(`l'elemento numero ${i} vale ${numeri[i]}`);
}

You write i < numeri.length and not i < 4: that way the code keeps working if tomorrow the array changes length. And in the final project it certainly does, because an array of points can hold 21 (a hand) or 33 (a whole body).

When you do not need the index, and only care about the value, there is a shorter and more readable form, for…of: 

const numeri: number[] = [10, 20, 30, 40];

for (const valore of numeri) {
  console.log(valore);
}

It reads literally: "for each valore of numeri". You use const because a new variable is born at every round. When to use which: if the value is enough, for…of; if you also need to know which position you are at — and to find the highest finger you do — then the classic for with the index.

There is a third way, while, which repeats as long as a condition stays true, with no automatic counter. You use it when you do not know in advance how many rounds you will need: 

let rimaste = 3;

while (rimaste > 0) {
  console.log(`mancano ${rimaste} prove`);
  rimaste = rimaste - 1;
}

It never appears in the hand project: when you work on lists of points you always know how many there are. It is useful to know it, not useful to use it today.

Last concept, and it is what makes TypeScript more than JavaScript: union types. What they are for: often a variable cannot hold any text, only two or three specific words. Telling the compiler avoids a whole family of errors. 

type Stato = "spenta" | "accesa";

let camera: Stato = "spenta";
camera = "accesa";    // ok
camera = "acesa";     // ERROR: Type '"acesa"' is not assignable to type 'Stato'.

The vertical bar | reads "or". Without the union type you would have written let camera: string, and that "acesa" with a single c would have slipped through: the program would have checked camera === "accesa", found false and turned nothing on, without a single error message. An afternoon wasted, for one letter.

Where you see it in the real project In the application's main.ts file there is exactly this line: type State = "idle" | "loading" | "running" | "error". They are the four possible states of the page: off, starting, running, in error. Nothing else is allowed, and the compiler enforces it.

We close with a trap worth its thirty seconds. const on an array does not make the array immutable: it only prevents replacing it with another array. 

const numeri: number[] = [1, 2, 3];

numeri.push(4);           // ALLOWED: the array is now [1, 2, 3, 4]
console.log(numeri);

numeri = [9, 9, 9];       // ERROR: Cannot assign to 'numeri' because it is a constant.

The reason: const protects the name, not the contents. The variable numeri will keep pointing at that list; what is inside the list is another matter. push adds an element at the end and is the normal way to build an array bit by bit.

Exercise 2.1 — Sum and average basic

Given the array below, compute and print the sum of all the numbers and their average. Copy the starting code and complete it. 

const numeri: number[] = [12, 7, 30, 4, 22];

let somma = 0;
// write here the loop that adds each number to `somma`

console.log(`somma: ${somma}`);
Solution 
const numeri: number[] = [12, 7, 30, 4, 22];

let somma = 0;
for (const valore of numeri) {
  somma = somma + valore;
}

const media = somma / numeri.length;

console.log(`somma: ${somma}`);    // 75
console.log(`media: ${media}`);    // 15

Why this way. The variable somma is declared outside the loop and with let: inside the loop it would be born and die at every round, and at the end there would be nothing left to print. For the average you divide by numeri.length and not by 5: if tomorrow you add a number, the code is already right.

Exercise 2.2 — Is the coordinate inside the image? basic

In the final project every point of the hand arrives with two coordinates between 0 and 1: 0 is the left (or top) edge of the image, 1 the right (or bottom) edge. Every now and then, when the hand leaves the frame, a value outside that range arrives.

Declare const x = 0.42; and write an if that prints "punto dentro l'immagine" if x is between 0 and 1 (ends included) and "punto fuori dall'immagine" otherwise. Then try changing x to 1.3 and to -0.2 and check that it answers correctly in all three cases.

Solution 
const x = 0.42;

if (x >= 0 && x <= 1) {
  console.log("punto dentro l'immagine");
} else {
  console.log("punto fuori dall'immagine");
}

Why this way. You need two comparisons joined by &&, because both conditions must be true. Watch out for the classic error: 0 <= x <= 1 is how you say it in maths, but in code it does not work — the computer first computes 0 <= x, gets a boolean, and then compares a boolean with 1. A meaningless result, and indeed the compiler complains.

Exercise 2.3 — How many fingers are raised medium

To recognize a gesture, the final project starts from five yes/no answers: thumb raised? index raised? and so on. We keep them in an array of five booleans, in order: thumb, index, middle, ring, little finger.

Count how many fingers are raised and print the number. Then, with an if, add a sentence: 0 fingers is a fist, 5 fingers is an open hand, any other number is "other". 

const alzate: boolean[] = [false, true, true, false, false];
Solution 
const alzate: boolean[] = [false, true, true, false, false];

let quante = 0;
for (const dito of alzate) {
  if (dito === true) {
    quante = quante + 1;
  }
}

console.log(`dita alzate: ${quante}`);   // 2

if (quante === 0) {
  console.log("pugno");
} else if (quante === 5) {
  console.log("mano aperta");
} else {
  console.log("altro");
}

Why this way. if (dito === true) can also be written just if (dito), because dito is already a boolean: the short form is the one you will find in real code. Here the long one was chosen because at the start it is clearer — what matters is knowing that they are the same thing.

Exercise 2.4 — The maximum and its position medium

Find the largest value in the array and also at which index it is. Print both. 

const numeri: number[] = [12, 7, 30, 4, 22];
Why it really matters This is not a textbook exercise. In the final project, to work out which finger is highest, you go through the five fingertips and look for the highest one: the value alone is not enough, because you need to know which finger it is. And the finger is the position in the list. Hence you must use the for with the index and not for…of.
Solution 
const numeri: number[] = [12, 7, 30, 4, 22];

let massimo = numeri[0];
let indiceDelMassimo = 0;

for (let i = 1; i < numeri.length; i++) {
  if (numeri[i] > massimo) {
    massimo = numeri[i];
    indiceDelMassimo = i;
  }
}

console.log(`il massimo è ${massimo}, alla posizione ${indiceDelMassimo}`);
// il massimo è 30, alla posizione 2

Why this way. You start from the first element as the champion to beat and the loop starts from i = 1: comparing the first with itself would be pointless. The two variables are always updated together, inside the same if: if only the value were updated, the index would stay the old one and the answer would be silently wrong.

A very common error is starting from let massimo = 0. It works with these numbers, but if the array held only negative numbers the answer would be 0, which is not even in the array. Starting from the first element is always correct.

const x: number[] = [
  0.50, 0.42, 0.36, 0.33, 0.30,
  0.44, 0.42, 0.41, 0.40,

  if (valore < 0.5) {
    sinistra = sinistra + 1;

Typical errors in class

  • Mixing up = and ===: if (dita = 5) does not compare, it assigns. The compiler helps here and flags the error, but the message is not intuitive: worth showing it before they meet it on their own.
  • Index starting from 1: for (let i = 1; i <= numeri.length; i++) skips the first element and reads one that does not exist. Double damage in a single line.
  • The variable declared inside the loop: let somma = 0 written inside the braces is reset at every round, and at the end only the last value is printed.
  • Forgotten braces: if (x > 0) console.log("a"); console.log("b"); always prints "b". Course rule: always use braces, even for a single line.
  • NaN printed on screen: almost always a numeri[i] read past the end of the array, or a division by a length equal to zero.
  • Infinite loop: the tab freezes. Close it, reopen the Playground, the code is in the address. No drama.

Quick check (5 questions)

Questions and answers
  1. How many rounds does for (let i = 0; i < 3; i++) do? → Three: with i equal to 0, 1 and 2.
  2. What is the last valid index of an array of 21 elements? → 20, that is length - 1.
  3. Why write === and not ==? → Because double equals converts types before comparing, and "5" == 5 comes out true. Triple equals also compares the type.
  4. What does console.log([1, 2, 3][5]) print? → undefined: that element does not exist.
  5. Can you push onto an array declared with const? → Yes. const prevents replacing the array, not changing its contents.

Theory

What it is for. Two reasons, in order of importance. The first is that giving a name to a piece of work makes it understandable: distanza(a, b) is clear at a glance, four lines of square roots are not. The second is that something written in one place is fixed in one place. If the same formula is copied in five places, sooner or later four are updated and one is not.

A function is a block of code with a name, which receives some input values and returns one as output. You declare it like this: 

function raddoppia(numero: number): number {
  return numero * 2;
}

console.log(raddoppia(5));    // 10
console.log(raddoppia(21));   // 42

Piece by piece, because each part has a name the teacher will use later:

  • function — the word announcing "I am about to declare a function".
  • raddoppia — the name. Choose a verb, because a function does something.
  • numero: number — the parameter, with its type. It is a variable that exists only inside the function.
  • : number after the round brackets — the return type: what comes out.
  • return — the statement that hands over the result and immediately ends the function.

raddoppia(5) is the call: the 5 goes in, takes the place of numero, and the function returns 10. The returned value can be printed, put in a variable, or fed to another function.

return shuts the door Everything after an executed return never runs. It is not a flaw, it is the useful part: if (dimensione === 0) return 0; at the start of a function is the standard way to deal with odd cases right away and then write the normal case without nesting five ifs inside each other.

There can be more than one parameter, separated by commas, each with its own type: 

function area(larghezza: number, altezza: number): number {
  return larghezza * altezza;
}

console.log(area(640, 480));   // 307200

Order matters. area(640, 480) and area(480, 640) give the same result here by chance, but not in general: the first value goes into the first parameter, full stop.

Some functions return nothing: they print, draw, switch on. Their return type is written void, which means "empty": 

function saluta(nome: string): void {
  console.log(`ciao ${nome}`);
}

saluta("Giulia");   // prints: ciao Giulia

const risultato = saluta("Marco");
console.log(risultato);   // undefined: there was nothing to return
How to recognize them If the function answers a question ("how long is it?", "how many fingers?") it returns a value. If instead it performs an action ("print", "draw", "turn off the camera") it is usually void. In the final project stop(), which turns everything off, is void; realSide(), which answers "is it the right or the left", returns a value.

There is a second, shorter way to write it, called an arrow function. It does exactly the same thing: 

const raddoppia = (numero: number): number => {
  return numero * 2;
};

// and when the body is a single expression, you can also drop return and the braces:
const triplica = (numero: number): number => numero * 3;

console.log(raddoppia(5));    // 10
console.log(triplica(5));     // 15

The function is put in a const as if it were any other value — because it is. This form is useful above all when a function must be passed to someone else, which is the next topic.

Parameters can have a default value, used when the caller does not pass one: 

function aPixel(valore: number, dimensione: number = 640): number {
  return valore * dimensione;
}

console.log(aPixel(0.5));        // 320  → uses 640
console.log(aPixel(0.5, 480));   // 240  → uses what you pass

Or they can be optional, with a question mark. In that case, if they are not passed, they are undefined, and the function must allow for it: 

function etichetta(nome: string, gesto?: string): string {
  if (gesto === undefined) {
    return nome;
  }
  return `${nome}: ${gesto}`;
}

console.log(etichetta("Destra"));               // Destra
console.log(etichetta("Destra", "pugno"));      // Destra: pugno
Optional parameters go last An optional parameter cannot come before a required one: the compiler rejects it, and rightly so — it would have no way to tell which value you skipped.

Functions can call other functions, and this is the normal way to build programs: you start from small, safe pieces and combine them. 

function distanza(x1: number, y1: number, x2: number, y2: number): number {
  const dx = x2 - x1;
  const dy = y2 - y1;
  return Math.sqrt(dx * dx + dy * dy);
}

function dimensioneMano(xPolso: number, yPolso: number, xNocca: number, yNocca: number): number {
  return distanza(xPolso, yPolso, xNocca, yNocca);
}

console.log(dimensioneMano(0.50, 0.88, 0.51, 0.58));   // about 0.3002

Math is a set of ready-made maths tools that the language provides: Math.sqrt is the square root, Math.abs the absolute value, Math.round rounding, Math.min and Math.max the smaller and the larger of two numbers.

Last piece for today: map and filter. They are two array tools that take a function as an argument. It looks odd the first time, so read them as plain sentences: 

const numeri: number[] = [1, 2, 3, 4];

// map: "make me a NEW array, applying this function to every element"
const doppi = numeri.map((n) => n * 2);          // [2, 4, 6, 8]

// filter: "make me a NEW array with only the elements for which this function says true"
const grandi = numeri.filter((n) => n > 2);      // [3, 4]

console.log(doppi);
console.log(grandi);
console.log(numeri);   // [1, 2, 3, 4] — the original was not touched

Neither of them changes the starting array: they return a new one. They are the short form of a for loop that builds an array with push, and in real code they are almost always used instead of that loop because they state the intention in one line.

We close with an idea, not a syntax. A function is called pure when, given the same inputs, it always returns the same output and touches nothing outside itself. distanza is pure: with those four numbers it will always answer the same, today and in a month. saluta is not, because it prints — it changes something in the outside world. Pure functions are easier to test and hold no surprises: when you can write one, do.

Exercise 3.1 — The distance between two points basic

Write the function distanza(x1, y1, x2, y2) that returns the distance between two points, using Math.sqrt. Test it with (0, 0) and (3, 4): it must give exactly 5.

Then rewrite it with Math.hypot, which directly computes the root of the sum of the squares, and check that the result is identical.

Solution 
function distanza(x1: number, y1: number, x2: number, y2: number): number {
  const dx = x2 - x1;
  const dy = y2 - y1;
  return Math.sqrt(dx * dx + dy * dy);
}

function distanzaBreve(x1: number, y1: number, x2: number, y2: number): number {
  return Math.hypot(x2 - x1, y2 - y1);
}

console.log(distanza(0, 0, 3, 4));        // 5
console.log(distanzaBreve(0, 0, 3, 4));   // 5

Why this way. dx and dy are the two legs of the triangle; the distance is the hypotenuse. Putting the two legs in two named consts, instead of writing everything in one line, makes the formula readable and avoids computing the same subtraction twice.

In the real project this is the line that measures how big the framed hand is: the distance between the wrist and the middle-finger knuckle. Exercise 3.3 — The average, but as a function basic

Write mediaDi(numeri: number[]): number, which returns the average of the elements. It must work with arrays of any length; if the array is empty it must return 0 instead of NaN.

Solution 
function mediaDi(numeri: number[]): number {
  if (numeri.length === 0) {
    return 0;
  }

  let somma = 0;
  for (const valore of numeri) {
    somma = somma + valore;
  }
  return somma / numeri.length;
}

console.log(mediaDi([12, 7, 30, 4, 22]));   // 15
console.log(mediaDi([0.4, 0.6]));           // 0.5
console.log(mediaDi([]));                   // 0

Why this way. The empty-array check is at the top and ends right away with a return: the odd case cleared out of the way before starting. Without it, the division would be 0 / 0, that is NaN, and that NaN would spread into all later calculations without saying where it came from.

      quante = quante + 1;

  }

Typical errors in class

  • Forgotten return: the function prints but does not return, and the caller gets undefined. If TypeScript knows the return type it flags it right away — a great reason to always write it.
  • Declaring and not calling: writing function distanza(…) and expecting something to happen. Declaring is like writing a recipe; calling is cooking.
  • Calling without the brackets: console.log(mediaDi) prints the text of the function, not the result. You need mediaDi(numeri).
  • Swapped parameters: aPixel(640, 0.5) gives 320 just like aPixel(0.5, 640) — multiplication forgives — but with distanza the wrong order produces nonsense. Better to get used to reading the signature right away.
  • Using a variable declared inside another function: parameters and consts declared inside a function exist only in there. The message is Cannot find name.
  • The semicolon after the arrow: const f = () => { … }; wants the final semicolon because it is a variable declaration; function f() { … } does not. Nobody remembers it, and that is perfectly fine: the formatter fixes it.

Questions and answers
  1. What is the difference between declaring and calling a function? → Declaring defines it, calling runs it. A function never called does nothing.
  2. What does : void mean? → That the function returns no value: it performs an action.
  3. What does [1, 2, 3].map((n) => n + 1) return? → A new array, [2, 3, 4]. The original stays [1, 2, 3].
  4. When do you put ? on a parameter? → When it is optional; inside the function it may be undefined and you must allow for it.
  5. What is a pure function? → One that, with the same inputs, always gives the same result and changes nothing outside itself.

Theory

What it is for. Try to imagine writing the final project with what you know now: twenty-one horizontal values in one array, twenty-one vertical ones in another, and the promise never to get the pairing wrong. A single sort on one array and the hand falls apart. An object keeps together the values that describe the same thing, and keeps them together by construction. 

const polso = { x: 0.50, y: 0.88 };

console.log(polso.x);   // 0.5
console.log(polso.y);   // 0.88
console.log(polso);     // { x: 0.5, y: 0.88 }

Between braces you list the properties: a name, a colon, a value, separated by commas. You read them with the dot: polso.x. That is all. If the variable is let, or if the property is not protected, you can also change them: 

const polso = { x: 0.50, y: 0.88 };

polso.x = 0.55;         // PERMESSO, anche con const (vale la stessa regola degli array)
console.log(polso.x);   // 0.55

polso.z = 0.1;          // ERRORE: Property 'z' does not exist on type '{ x: number; y: number; }'.

That last error is already TypeScript at work: it worked out the shape of the object by itself and does not accept made-up properties. But that shape is written in one place only, and if tomorrow we needed it in ten different functions we would have to copy it ten times. That is why interface exists: it gives a name to a shape. 

interface Punto {
  x: number;
  y: number;
  z?: number;     // il punto interrogativo: facoltativa
}

const polso: Punto = { x: 0.50, y: 0.88 };
const puntaIndice: Punto = { x: 0.40, y: 0.37, z: -0.02 };

console.log(polso.x, puntaIndice.z);

Inside the interface, properties are separated by semicolons (or new lines) and not by commas as in objects: it is the number one confusion of the lesson. From here on Punto is a type in every respect, and it is used like number or string: as the type of a variable, of a parameter, of a return value, and inside an array. 

const punti: Punto[] = [
  { x: 0.50, y: 0.88 },
  { x: 0.40, y: 0.37 },
  { x: 0.51, y: 0.58 },
];

console.log(punti.length);   // 3
console.log(punti[1].x);     // 0.4  → l'elemento 1, e di quello la x

for (const p of punti) {
  console.log(`(${p.x}, ${p.y})`);
}

punti[1].x reads from left to right: take the element at index 1, and of that object take the property x. This line, as punti[8].x, will appear dozens of times in the real project: 8 is the tip of the index finger.

A property can be declared readonly: it can be read, not rewritten. It says "this data, once created, must not be touched". 

interface PuntoFisso {
  readonly x: number;
  readonly y: number;
}

const origine: PuntoFisso = { x: 0, y: 0 };
origine.x = 5;   // ERRORE: Cannot assign to 'x' because it is a read-only property.

Now the most important part of the lesson, the one that separates those who will write solid programs from those who will spend their evenings hunting bugs: values that might not be there. There are two, and they mean slightly different things:

  • undefined — "nothing was ever put here". It is what you get from an optional property with no value, from an optional parameter that was not passed, or from an element past the end of an array.
  • null — "here, on purpose, there is nothing". A programmer writes it to say "this slot is empty, and I know it".

Both appear in the final project: let stream: MediaStream | null = null means "the webcam is off right now, and it is not an oversight". The problem is that reading a property of a value that is not there blows up the program: 

interface Punto { x: number; y: number }

let punta: Punto | undefined = undefined;

console.log(punta.x);   // ERRORE del compilatore: 'punta' is possibly 'undefined'.
                        // e se lo eseguissi davvero: TypeError, il programma si ferma

There are three ways to handle it, in order of elegance. The first is optional chaining ?.: it tries to read, and if there is nothing in front it returns undefined instead of blowing up. 

let punta: Punto | undefined = undefined;

console.log(punta?.x);   // undefined — nessun errore

The second is the fallback value ??, which reads "otherwise": if what is on the left is undefined or null, it takes what is on the right. The two are almost always used together: 

let punta: Punto | undefined = undefined;

const x = punta?.x ?? 0;
console.log(x);   // 0

punta = { x: 0.40, y: 0.37 };
console.log(punta?.x ?? 0);   // 0.4
?? is not || They look interchangeable and they are not. || fires on any "empty" value, and for it zero is empty too: 0 || 0.5 gives 0.5. With hand coordinates that is a disaster, because 0 is the left edge of the image, a legitimate value. 0 ?? 0.5 instead gives 0, which is the right answer. Rule: for missing values use ??.

The third way is type narrowing: an if that checks, and inside which the compiler knows the value is there. It is the clearest when you need to use the value more than once: 

function stampaPunto(punto: Punto | undefined): void {
  if (punto === undefined) {
    console.log("nessun punto");
    return;
  }

  // da qui in poi TypeScript sa che `punto` esiste: niente ?. e niente errori
  console.log(`x vale ${punto.x} e y vale ${punto.y}`);
}

stampaPunto(undefined);              // nessun punto
stampaPunto({ x: 0.4, y: 0.37 });    // x vale 0.4 e y vale 0.37

The compiler follows the reasoning: after that return, the only way to still be there is that punto is not undefined. It is not magic, it is the same thing you would have thought reading the code — only it checks it for you.

interface or type? You can also write type Punto = { x: number; y: number }, and for the cases in this course the two forms are equivalent. Course convention, so we never have to think about it again: interface to describe the shape of an object, type for aliases and for union types like type Gesto = "pugno" | "mano aperta", which you cannot even write with interface.

Exercise 4.2 — The centre of the hand medium

Write centro(punti: Punto[]): Punto, which returns the midpoint of a list: the x of the result is the average of the x values, the y is the average of the y values. Try it on the mano array given in the theory.

Solution 
function centro(punti: Punto[]): Punto {
  if (punti.length === 0) {
    return { x: 0, y: 0 };
  }

  let sommaX = 0;
  let sommaY = 0;
  for (const p of punti) {
    sommaX = sommaX + p.x;
    sommaY = sommaY + p.y;
  }

  return { x: sommaX / punti.length, y: sommaY / punti.length };
}

const c = centro(mano);
console.log(`il centro della mano sta in (${c.x}, ${c.y})`);
// il centro della mano sta in (0.49, 0.5911111111111111)

Why this way. You go through the array only once, accumulating two sums: two separate loops would work but would be double the work. The return builds a new object on the spot — there is no need to declare it first in a variable.

In the real project the centre is used to decide where to place the hand in the scene, and to tell whether it is moving: if the centre moves a lot from one frame to the next, the hand is moving fast, and the anti-jitter filter of lesson 9 will behave accordingly.

Exercise 4.3 — The highest point medium

Write piuAlto(punti: Punto[]): Punto, which returns the highest point in the list. Try it on the mano array: it must return the middle fingertip, that is { x: 0.51, y: 0.33 }.

y grows DOWNWARDS This is the most expensive trap in the whole project, and everyone falls into it at least once. In images, and on screen, the origin is at the top left: y = 0 is the top edge, y = 1 is the bottom one. So "higher" means "smaller y", and the function must be written by looking for the minimum, not the maximum. At school the Cartesian plane went the other way round; here it does not. In the real project this inversion is paid for again when moving to the three-dimensional scene, where y goes back to growing upwards and has to be flipped once more.
Solution 
function piuAlto(punti: Punto[]): Punto {
  let migliore = punti[0];

  for (const p of punti) {
    if (p.y < migliore.y) {   // SMALLER y = higher in the image
      migliore = p;
    }
  }

  return migliore;
}

const alto = piuAlto(mano);
console.log(`il punto più in alto è (${alto.x}, ${alto.y})`);
// il punto più in alto è (0.51, 0.33)  → the middle fingertip

Why this way. It is the maximum of exercise 2.4 with the comparison flipped and, above all, with objects instead of numbers: we keep aside the whole point, not just the coordinate, so whoever calls the function also gets the x without having to look for it again. The comment on the comparison line is not decoration: six months from now it will be the only thing stopping you from "fixing" that < into >.

If you finish early: make it return the index too, as in lesson 2. You will need the for with a counter and to return an object with two properties, for example { punto: …, indice: … }.

// mano destra · 9 punti · centro (0.490, 0.591) · gesto: nessuno

In the real project this is almost exactly the structure that comes from the recognizer: for each hand in the frame there is the side, the twenty-one points and, optionally, the name of the gesture recognized among the known ones. And the side, in the real code, is a union type identical to this one.

Typical mistakes in class

  • Comma inside the interface: you write x: number; with a semicolon (or just a new line). With a comma the compiler complains and the message is not very clear.
  • Colon instead of the equals sign: const polso = { x: 0.5 } inside the object wants the colon, but the variable is created with the equals sign. Mixing the two up is perfectly normal on the first day.
  • Braces in the return: return { x: 1, y: 2 }; returns an object. The braces here are not a code block, they are the object: people end up hunting a non-existent error because of this.
  • Looking for the maximum to find the highest point: in images y grows downwards. If the drawn hand comes out upside down, the problem is almost always here.
  • Using || instead of ??: it works until a legitimate zero arrives, and then it breaks in a way that is very hard to track down.
  • Comparing objects with ===: { x: 1 } === { x: 1 } is false. The comparison checks whether they are the same object, not whether they have the same content. To compare content you compare the properties one by one.

Quick check (5 questions)

Questions and answers
  1. What does z?: number mean inside an interface? → That the property is optional: if it is missing its value is undefined.
  2. What does punti[99]?.x return if the array has 21 elements? → undefined, without blowing up the program.
  3. In the image, which is the higher point: the one with y 0.2 or the one with y 0.8? → The one with y 0.2. y grows downwards.
  4. Why does 0 ?? 5 give 0 while 0 || 5 gives 5? → Because ?? fires only on null and undefined, || on any value considered "empty", zero included.
  5. Can you change a property of an object declared with const? → Yes, unless it is readonly. const protects the name, not the content.

Theory

What it is for. Nobody looks at a program that prints numbers in a console. The final project is a web page: there is a button, there is a box with the webcam and there is a canvas on which the hand appears. Today we learn the two mechanisms that hold the code and what you see together: getting an element of the page and drawing inside it.

Let us start with the page. An HTML page is made of tags, which open and close and contain other tags. This is the smallest one we need: 

<!doctype html>
<html lang="it">
  <head>
    <meta charset="UTF-8" />
    <title>La mia mano</title>
  </head>
  <body>
    <canvas id="tela" width="480" height="640"></canvas>
    <script type="module" src="/src/main.ts"></script>
  </body>
</html>

<head> contains information about the page, <body> what you see. The <canvas> is the canvas: an empty rectangle, here 480 pixels wide and 640 high, inside which the code can draw. The id is the name the code will look it up by: it must be unique in the page. The last line loads our program.

On StackBlitz vite.new/vanilla-ts opens a ready-made project in about ten seconds, with the preview on the right that updates by itself on every save. Two files matter: index.html, whose <body> content you will replace, and src/main.ts, which you can empty completely before starting. It is exactly the same tool you will install on your own computer in lesson 6: nothing is thrown away.

Now the code has to get hold of that <canvas>. You ask the page for it by name: 

const tela = document.getElementById("tela");

document is the page, as seen from the code. getElementById looks for the element with that id. But if you try to use it, TypeScript gets in the way: 

const tela = document.getElementById("tela");
console.log(tela.width);
// ERRORE: 'tela' is possibly 'null'.
// ERRORE: Property 'width' does not exist on type 'HTMLElement'.

Two complaints, and both are right:

  1. It might not be there. The return type is HTMLElement | null: that union type says "an element, or nothing". If you misspelled the id, or if the code starts before the page is ready, the answer is null. It is the same null as in lesson 4.
  2. It does not know what kind of element it is. It knows it is an element of the page, HTMLElement, and that is all. But a heading has no drawing width, a canvas does: until the compiler knows it is a canvas, it will not let you use canvas things.

The second problem is solved with as, which reads "treat it as": it is a promise you make to the compiler. 

const tela = document.getElementById("tela") as HTMLCanvasElement | null;

if (!tela) {
  throw new Error("canvas non trovato: controlla l'id nell'HTML");
}

console.log(tela.width);   // 480 — adesso va

if (!tela) reads "if tela is NOT there": it is the exclamation mark from lesson 2, the one that flips things. After that block the compiler knows that tela exists — it is the same narrowing as in lesson 4.

as is a promise, not a check Writing as HTMLCanvasElement verifies nothing: it convinces the compiler and that is it. If in the HTML that id is on a <div>, the program will break anyway, only later and with a more obscure message. You use as when you know what the page looks like because you wrote it — and that is exactly the case in our project, where the ids are written by hand and never change.

You do not draw directly on the canvas: you ask for the context, that is the object that holds all the drawing tools. There are several kinds; we need the two-dimensional one. 

const ctx = tela.getContext("2d");

if (!ctx) {
  throw new Error("contesto 2d non disponibile");
}

This too can return null (for example if the same canvas had already been asked for a context of a different kind), so you check it as before. From here on ctx is the object you draw everything with.

Coordinates. Before drawing you need to know where things will end up. The canvas has its origin at the top left: x grows to the right, y grows downwards. It is the same convention as images seen in lesson 4 — and for once this is an advantage: the recognizer's coordinates, multiplied by the canvas size, end up in the right place without flipping anything. 

// su una tela 480 × 640:
// (0, 0)     angolo in alto a sinistra
// (480, 0)   angolo in alto a destra
// (0, 640)   angolo in basso a sinistra
// (240, 320) centro esatto

function aPixel(valore: number, dimensione: number): number {
  return valore * dimensione;
}

console.log(aPixel(0.5, 480));   // 240 → metà della larghezza

Drawing a circle. You need it for the joints of the hand. It takes a few lines, always the same: 

ctx.beginPath();                              // 1. inizia un disegno nuovo
ctx.arc(240, 320, 8, 0, Math.PI * 2);         // 2. descrivi un cerchio
ctx.fillStyle = "#38bdf8";                    // 3. scegli il colore di riempimento
ctx.fill();                                   // 4. riempilo

The arguments of arc, in order: centre x, centre y, radius, start angle, end angle. 0 and Math.PI * 2 are the start and the end of a full turn: it is the recipe for "whole circle", and you copy it as it is.

beginPath is not optional Without it, every new shape is added to the previous ones in the same drawing: changing colour recolours them all, and the circles end up joined by mysterious lines. If drawing the twenty-one points of the hand gives you a spider web, this is the cause. Rule: one shape, one beginPath.

Drawing a line. You need it for the bones. Same pattern:

ctx.beginPath();
ctx.moveTo(100, 100);            // porta la penna qui, senza disegnare
ctx.lineTo(300, 400);            // traccia fino a qui
ctx.strokeStyle = "#f472b6";     // colore della linea
ctx.lineWidth = 4;               // spessore in pixel
ctx.stroke();                    // disegna davvero

The difference between fill and stroke is the same as between filling and outlining: fillStyle/fill for the inside, strokeStyle/stroke for the edge. Colours are written in hexadecimal ("#38bdf8") or by name ("white"). And nothing is actually drawn until you call fill or stroke: the instructions before only describe the shape.

Clearing. When the hand moves you do not draw over the previous one: you clear everything and redraw from scratch, thirty times a second. 

ctx.clearRect(0, 0, tela.width, tela.height);   // svuota tutta la tela

Responding to a click. The last tool for today. You get the button the way you got the canvas, and you tell it what to do when it is pressed: 

const pulsante = document.getElementById("cambia") as HTMLButtonElement | null;

if (pulsante) {
  pulsante.addEventListener("click", () => {
    console.log("premuto!");
  });
}

addEventListener wants two things: the name of the event ("click") and a function to run when it happens. That function is an arrow function with no parameters, from lesson 3. Nobody calls it explicitly: the browser calls it, when and if the user presses. In the final project this is exactly how the webcam starts, from the click on the "Turn on camera" button.

Typical mistakes in class

  • White page and no error: almost always the id in the HTML and the one in the code do not match, or the line <script type="module" src="/src/main.ts"> is missing. First place to look: the browser console.
  • The spider web: beginPath forgotten inside the loop. All the circles end up joined by lines.
  • Nothing shows but no error: fill or stroke forgotten. The drawing was described but not executed.
  • The upside-down hand: someone "fixed" y thinking 0 was at the bottom. In the canvas y grows downwards, as in the image: leave it as it is.
  • The canvas sized with CSS: setting width and height outside the width and height attributes stretches the drawing instead of enlarging it. For today: attributes in the HTML only.
  • Tiny hand in a corner: someone used aPixel(p.x, 1) or forgot to multiply. Coordinates 0…1 without multiplication all sit in the first pixel.
  • The button does not respond: the listener was registered on a null element inside an if that is never true, or the id is wrong.

Quick check (5 questions)

Questions and answers
  1. Why does document.getElementById return HTMLElement | null? → Because that id might not exist in the page: the type says so, and forces you to check.
  2. What does as HTMLCanvasElement do? → It convinces the compiler that the element is a canvas. It verifies nothing: it is a promise by whoever writes it.
  3. What is beginPath for? → To start a new shape, separate from the previous one. Without it, shapes get joined.
  4. Where is the point (0, 0) of a canvas? → At the top left. y grows downwards.
  5. What is the difference between fill and stroke? → fill fills the inside of the shape, stroke draws its outline.

Theory

In the first five lessons you wrote code inside a page that someone else kept open for you. It worked very well for learning, but now there is a precise obstacle: the webcam does not turn on inside the preview of online environments. The box that shows the result is a page framed inside another, coming from a different site, and browsers deny camera and microphone to those frames. It is not a flaw of the environment: it is a rule designed to stop any site from turning on your camera by hiding inside a frame.

From the next lesson you need the webcam. So today you need a real project.

Node.js: JavaScript outside the browser

Node.js is a program that runs JavaScript on your computer, without a browser. You do not need it to run the hand — that will run in the browser as always — but the tools need it: the TypeScript compiler, the development server, the program that puts the files together. They are all written in JavaScript and run on Node.

Together with Node you install npm (node package manager), which does two things:

  • it downloads libraries written by others — in lesson 8 you will download Google's hand recognizer with one command;
  • it runs the project's commands, the ones written in package.json: npm run dev, npm run build.
Do not mix up the two worlds Node runs on your computer and can open files and folders, but it does not know what a web page is: there document and window do not exist. The browser is the opposite. Your hand code lives in the browser; Node prepares it and serves it.

Vite: the ready-made project

Creating the right folder, the right configuration file and the right server by hand is boring and teaches nothing. Vite does it for you with one command: 

npm create vite@latest mano-corso

It asks you two questions. For the first (Select a framework) choose Vanilla, which means "no framework, just the page and the code". For the second (Select a variant) choose TypeScript. In short people say "the vanilla-ts template", and you can also ask for it directly: 

npm create vite@latest mano-corso -- --template vanilla-ts

Inside the newly created folder you find this:

mano-corso/
├── index.html          ← la pagina: il titolo, i pulsanti, il canvas
├── package.json        ← il "documento d'identità" del progetto
├── tsconfig.json       ← le regole del compilatore TypeScript
├── public/             ← file serviti così come sono (immagini, icone)
└── src/
    ├── main.ts         ← il codice che parte all'apertura della pagina
    └── style.css       ← l'aspetto

At the bottom of index.html there is a single line that links the page to the code: 

<script type="module" src="/src/main.ts"></script>

Then two commands, always the same, for the rest of the course:

cd mano-corso     # entra nella cartella
npm install       # scarica gli strumenti: crea node_modules/ (pesante, non si tocca)
npm run dev       # avvia il server di sviluppo

npm run dev prints an address, usually http://localhost:5173. You open it in the browser and see your page. The server stays on: leave that terminal window open and write the code in the other window. Every time you save, the page updates by itself in a fraction of a second. To stop it: Ctrl + C.

localhost means "this computer". Nobody outside sees that page. And it is also an address the browser trusts: as you will see next lesson, the webcam turns on only on https://… or on localhost, and that is why the local project works straight away.

The two configuration files

package.json is a text file that describes the project: the name, the libraries it uses and the available commands. 

{
  "name": "mano-corso",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc && vite build",
    "preview": "vite preview"
  },
  "devDependencies": {
    "typescript": "~5.9.0",
    "vite": "^7.0.0"
  }
}

What is in scripts are shortcuts: npm run dev runs what is written next to "dev". What is in devDependencies are the tools downloaded by npm install. The number next to the name is the version, and it matters: in lesson 8 you will see what happens when a library changes under a project's feet.

tsconfig.json tells the compiler how strict to be. The line we care about today is one: 

{
  "compilerOptions": {
    "target": "ES2022",
    "strict": true
  },
  "include": ["src"]
}

With "strict": true TypeScript stops letting things slide. The two checks you will notice straight away:

  • no accidental any: a parameter without a type becomes an error, because "I don't know" is not an acceptable answer;
  • no hidden null: if something might not exist — like document.getElementById("tela"), which returns the element or null — you have to say what to do in that case. 
// con strict acceso
const tela = document.getElementById("tela");
tela.textContent = "ciao";
// Errore: 'tela' is possibly 'null'.

// due modi onesti per risolverlo
const tela = document.getElementById("tela") as HTMLCanvasElement;   // "fidati, esiste"
// oppure, meglio:
const tela = document.getElementById("tela");
if (!tela) throw new Error("manca l'elemento #tela nella pagina");
Why accept being told off Every error that strict shows you now is an error that will not show up in lesson 8, while you move your hand in front of the webcam and cannot understand why the screen stays black. The right moment to find out that something can be null is when you write it.

Splitting the code into files: export and import

The real hand project — the one you see online — is split into five files, each with one job: turning on the camera, recognizing the hand, damping the jitter, drawing, putting it all in order. It is not fussiness: it is the only way to find things again.

A file becomes a module the moment it exports something. Whatever is not exported stays private to that file. 

// src/disegna.ts
export interface Punto {
  x: number;
  y: number;
  z: number;
}

const COLORE_OSSA = "#38bdf8";   // niente export: la usa solo questo file

export function disegnaPunti(ctx: CanvasRenderingContext2D, punti: Punto[]): void {
  for (const p of punti) {
    ctx.beginPath();
    ctx.arc(p.x, p.y, 4, 0, Math.PI * 2);
    ctx.fill();
  }
}
// src/main.ts
import { disegnaPunti, type Punto } from "./disegna";

const punti: Punto[] = [{ x: 100, y: 50, z: 0 }];
// disegnaPunti(ctx, punti);

Three things to notice, and they are always the same three:

  1. between braces you write the same names used in the export: if there it is disegnaPunti, here it cannot be DisegnaPunti;
  2. the path starts with ./ (same folder) or ../ (folder above), and you do not write the .ts extension;
  3. to import a type you write type before the name: it tells the compiler "this is only for you, it will not end up in the executed code".

What the compiler really does

The browser does not know what TypeScript is. It has never known what types are and it will not learn. What happens is simpler than it looks: the types are erased. 

// quello che scrivi tu (TypeScript)
function distanza(a: Punto, b: Punto): number {
  const dx: number = a.x - b.x;
  const dy: number = a.y - b.y;
  return Math.sqrt(dx * dx + dy * dy);
}

// quello che arriva al browser (JavaScript)
function distanza(a, b) {
  const dx = a.x - b.x;
  const dy = a.y - b.y;
  return Math.sqrt(dx * dx + dy * dy);
}

Identical, minus the annotations. Two consequences follow that are worth fixing in your mind now:

  • types cost nothing to whoever runs the program: by then they are already gone;
  • types do not protect you while the program runs. If in lesson 8 the recognizer returns zero hands, no type stops it: you will have to check it yourself with an if.

During development Vite does this transformation, on the fly, on every save. Type checking instead is done by tsc, which runs when you launch npm run build and continuously inside VS Code, which is why the red underlines appear while you type.

Typical mistakes in class

  • Command run in the wrong folder: npm run dev answers "Could not read package.json". The cd mano-corso is missing. The terminal always shows which folder you are in: read it before typing.
  • Spaces or accents in the path: a folder called Documenti scuola/progètto will sooner or later cause trouble. Use short, lowercase names, without spaces.
  • The server is already on: "Port 5173 is in use". Vite picks another one and says so — or you stop the first with Ctrl + C.
  • The page is white: almost always an error in main.ts. Open the browser console with F12 and read. The console is the first place to look, not the last.
  • "I fixed it but the error is still there": the file was not saved. Ctrl + S. The dot next to the file name, at the top, means "not saved".
  • import path without ./: import { … } from "disegna" makes it look for a library called "disegna" inside node_modules. You need "./disegna".
  • node_modules "takes up too much space": yes, hundreds of megabytes, and that is normal. Do not touch it, do not copy it, do not put it on a USB stick: it is recreated in thirty seconds with npm install.

Theory

Some things are not ready right away

Until now every line of code gave its result immediately. Turning on the webcam does not: the browser has to ask the user for permission, and the user may think about it for five seconds; then it has to turn on a physical camera. Meanwhile the program cannot stop: if it stopped, the page would freeze and not even the «Allow» button would work.

JavaScript's solution is called Promise: not the result, but the promise of a result. A function like getUserMedia gives you a promise right away, and sooner or later that promise is kept (the video stream arrives) or broken (the user said no).

To work with promises there are two words: 

async function accendi() {
  const flusso = await navigator.mediaDevices.getUserMedia({ video: true });
  console.log("acceso!", flusso);
}
  • await means «wait until this promise is kept, then give me the value». While it waits, the rest of the page keeps working: buttons respond, animations run.
  • async in front of function is the permission to use await inside it. If you forget it, the compiler tells you right away.
The type of an asynchronous function An async function always returns a promise, even when inside you write return 5. That is why its return type is written Promise<number>, and when it returns nothing Promise<void>. Those angle brackets say «a promise of what». 
async function accendiCamera(video: HTMLVideoElement): Promise<MediaStream> {
  const flusso = await navigator.mediaDevices.getUserMedia({ video: true, audio: false });
  video.srcObject = flusso;
  await video.play();
  return flusso;
}

When it goes wrong: try / catch

A promise can break, and with the webcam it breaks often: permission denied, no camera, camera already used by another program. If you do nothing, the user sees a page that does not react and does not understand why. 

try {
  flusso = await accendiCamera(video);
  // you only get here if it went well
} catch (e) {
  // you only get here if it went badly
  console.log("non ha funzionato:", e);
}

The browser does not send you a sentence, it sends you an error with a name. The three you will see in class today:

NameWhat happenedWhat to tell the user
NotAllowedErrorThe user denied permission, or had already denied it in the past«Allow camera use in the browser settings and try again»
NotFoundErrorNo webcam is connected«No webcam found on this device»
NotReadableErrorThere is one, but another program is using it«The webcam is busy with another application»

Translating them is trivial and changes everything: it is the difference between an application and a homework exercise.

The secure context

The webcam only turns on if the page comes from https://… or from localhost. On a plain http://, navigator.mediaDevices does not exist at all: the code fails with an obscure error.

The reason is serious. On http:// anyone in the middle of the network — the wi-fi operator, for instance — can change the page while it travels, and so make a page that had not asked for it turn on the camera. https prevents this. localhost is allowed because it travels nowhere: it is your computer. 

if (!window.isSecureContext || !navigator.mediaDevices?.getUserMedia) {
  throw new Error("La camera funziona solo su una pagina HTTPS o su localhost.");
}

It is exactly the check the real project does, before anything else. And it also explains why in lesson 10, when we talk about putting the site online, HTTPS will not be an optional detail.

Where the video ends up

The webcam stream does not show itself: it has to be attached to a <video> element. 

<video id="video" autoplay muted playsinline></video>
<canvas id="tela" width="640" height="480"></canvas>

Three attributes, three reasons:

  • autoplay — it starts by itself, without a second click;
  • muted — without it browsers block autoplay; and we do not need audio anyway, in fact we ask for audio: false;
  • playsinline — on phones it stops the video from opening full screen and swallowing the page.

The <video>, though, is only a little window. To draw the hand landmarks on top you need the canvas, and first you have to copy the image into it: 

ctx.drawImage(video, 0, 0, tela.width, tela.height);

One line, and the current frame is in the canvas. From there on you draw whatever you want on top: in lesson 8 it will be 21 dots.

The frame loop

Drawing once is not enough: the image changes all the time. You need a loop that restarts at every frame, and the browser provides it: 

function ciclo(): void {
  requestAnimationFrame(ciclo);          // book the next round
  ctx.drawImage(video, 0, 0, tela.width, tela.height);
}
ciclo();                                  // you call the first round yourself

requestAnimationFrame — «request an animation frame» — tells the browser: call me back just before the next screen repaint. It is usually 60 times a second.

Why not a timer, that is setInterval(ciclo, 16)? Three concrete reasons:

  • the timer does not know when the screen repaints, so now and then you draw twice between one repaint and the next (wasted work) or zero times (a visible stutter);
  • if the computer is slow, timers pile up and the page chokes; requestAnimationFrame instead simply skips a round;
  • when you switch tab, the browser suspends requestAnimationFrame: no battery spent drawing a page nobody is looking at. The timer would keep going regardless.

The loop is stopped with cancelAnimationFrame, and to do that you must have kept the number that requestAnimationFrame returns: 

let idCiclo = 0;

function ciclo(): void {
  idCiclo = requestAnimationFrame(ciclo);
  // …drawing…
}

function fermaCiclo(): void {
  cancelAnimationFrame(idCiclo);
}

Really turning the camera off

This is the part almost everyone gets wrong the first time. Pausing the <video> does not turn off the camera: the stream stays open and the little light next to the lens stays on. You have to stop the tracks, that is the individual channels of the stream, one by one: 

function spegniCamera(video: HTMLVideoElement, flusso: MediaStream | null): void {
  flusso?.getTracks().forEach((t) => t.stop());   // ← this is the line that matters
  video.pause();
  video.srcObject = null;
}

The check is physical and leaves no room for argument: the webcam light must go off. If it stays on, you have turned nothing off.

Typical mistakes in class

  • Permission denied by mistake the first time: the browser remembers and does not ask again, so the page looks broken. Fix it from the camera icon in the address bar. Show this to everyone before the lab, not after.
  • await outside an async function: compiler error. The little word async goes in front of the function that contains the await.
  • The video shows but the canvas is black: the loop has not started, or the canvas has zero width and height. The canvas width and height are written as HTML attributes, not as CSS.

  • The webcam does not start in the online environment: it is the framed preview. From here on you work locally, or in pairs with someone who has it; the preview in a separate tab is the last resort (lesson 6).

Theory

What a model is, in two paragraphs

Until now every line of your program told the computer exactly what to do: «draw a circle here», «multiply this by that». Finding a hand in an image cannot be done that way: nobody knows how to write the rules to recognize a hand — in any light, any skin, any ring, any background. People tried for twenty years.

A model is a different approach: instead of rules, examples. Someone — Google, here — collected tens of thousands of photographs of hands and marked by hand, on each one, where the 21 joints are. Then a training program adjusted millions of internal numbers, a little at a time, until the system started guessing those 21 points even on photographs it had never seen. The result of that work is a file: gesture_recognizer.task, eight megabytes of numbers. It contains no photographs, no hands: only the numbers needed to do that calculation.

Three practical things follow from this, worth having clear:

  • The model is downloaded once and runs on your computer. There is no server to query: the image of your hand never leaves the browser. That is the reason this project can promise what it promises.
  • The model makes mistakes. Not «may make mistakes»: it does, and you will see it today. Against the light, with the hand tilted or half out of the frame, the points jitter or the hand disappears. It is not your bug: it is the nature of the thing, and in lesson 9 you will learn to live with it.
  • The model understands nothing. It gives numbers, and the numbers have a confidence. It does not know what a hand is, it does not know it is yours.

Installing a library, and pinning its version

npm install @mediapipe/tasks-vision@1.0.1

This command downloads Google's library into node_modules and adds a line to package.json. That @1.0.1 at the end is the important part of the lesson. 

"dependencies": {
  "@mediapipe/tasks-vision": "1.0.1"
}

Written like this — without ^, without ~, without @latest — it means «exactly this version». Anyone who installs the project two years from now will get the very same files, and the project will work as it does today.

Why «the latest version» is a terrible idea With @latest your project changes by itself, on a day you did not choose, while you are not looking. One morning you open it and it no longer works, and you touched nothing: it is one of the most frustrating experiences in the trade. In the real hand project three things are pinned precisely, and they must be aligned with each other: the library, the wasm folder that goes with it and the .task model file. Google's official documentation uses @latest in its examples. That is fine for an example; not for something that has to keep working. Do not confuse it with the lesson 6 command, npm create vite@latest: there @latest is the version of the tool that creates the folder once, not a dependency that stays in the project.

Loading the recognizer

You need two addresses: the runtime (the calculation engine, written in WebAssembly) and the model. Loading takes time — about twenty megabytes the first time — so it is all async, like last lesson's webcam. 

// src/tracker.ts
import { FilesetResolver, GestureRecognizer } from "@mediapipe/tasks-vision";

const WASM = "https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@1.0.1/wasm";
const MODELLO =
  "https://storage.googleapis.com/mediapipe-models/gesture_recognizer/gesture_recognizer/float16/1/gesture_recognizer.task";

export async function creaRiconoscitore(): Promise<GestureRecognizer> {
  const vision = await FilesetResolver.forVisionTasks(WASM);
  return GestureRecognizer.createFromOptions(vision, {
    baseOptions: { modelAssetPath: MODELLO },
    runningMode: "VIDEO",
    numHands: 1,
  });
}

Line by line, the three things that matter:

  • FilesetResolver.forVisionTasks prepares the engine: it looks at what your processor can do and picks the right WebAssembly variant by itself.
  • runningMode: "VIDEO" says «you will get frames in sequence, not unrelated photos». In this mode the recognizer follows the hand from one frame to the next instead of searching for it from scratch every time: it is much faster and much more stable. The alternative is "IMAGE", for single photographs.
  • numHands: 1 — one hand is enough to start. Setting it to 2 is exercise 8.5.
In the real project the files do not come from the internet The hand site keeps runtime and model on its own domain, copied during the site build. Two reasons: this way the page contacts nobody else — and the promise «the images do not leave the browser» becomes verifiable instead of just stated — and the files stay those of the pinned version, not whatever a public CDN serves today. For today, in class, the CDN is perfectly fine: it is one less address to configure.

Asking for the points, at every frame

const risultato = riconoscitore.recognizeForVideo(video, performance.now());

This line goes inside the loop from lesson 7. Two details, both sources of mistakes on the first day:

  1. It is not await. In VIDEO mode the calculation happens immediately and returns the result immediately. It is also why, if the computer is slow, the fps collapse: drawing waits for recognition.
  2. The time must always increase. The second parameter is the moment of the frame, in milliseconds. If you pass a time equal to or less than the previous one, the library stops with an error. With performance.now() it does not happen, because a clock moves forward — but you need to know the rule, because it causes an error that otherwise looks incomprehensible.

There is also a trick that saves half the work. The screen repaints 60 times a second, but the webcam sends 30 frames a second: half of the loop's rounds see the same image as before. Analysing it twice is wasted work: 

let ultimoIstante = -1;

function ciclo(): void {
  idCiclo = requestAnimationFrame(ciclo);

  // readyState >= 2 means "a frame is ready"
  if (video.readyState >= 2 && video.currentTime !== ultimoIstante) {
    ultimoIstante = video.currentTime;
    const risultato = riconoscitore.recognizeForVideo(video, performance.now());
    disegnaTutto(risultato);
  }
}

What the result looks like

risultato.landmarks is an array of hands; each hand is an array of 21 points; each point has x, y, z. Three levels, and you have to keep them apart: 

risultato.landmarks            // [ [21 points], [21 points] ]  ← 0, 1 or 2 hands
risultato.landmarks[0]         // the 21 points of the first hand
risultato.landmarks[0][8]      // the index fingertip
risultato.landmarks[0][8].x    // 0.42 — a number between 0 and 1
FieldMeaningRange
xhorizontal position on the image0 = left edge … 1 = right edge
yvertical position0 = top … 1 = bottom
zdepth relative to the wristsame scale as x; negative = closer to the camera

They are the same 0-to-1 coordinates as the fake hand in lesson 5, and that is no accident: the course was built so that today you have to change just one line. They are numbers relative to the image, not pixels: if tomorrow you change the size of the canvas, the points keep working.

And the point numbers are always the same, for everyone: 0 the wrist, 4 the thumb tip, 8 the index fingertip, 12 the middle finger, 16 the ring finger, 20 the little finger. They are the numbers you already used in the bone table in lesson 6.

When the hand is not there

If you take your hand out of the frame, landmarks is an empty array. Writing risultato.landmarks[0][0].x without checking blows the program up. The ?. from lesson 4 is for exactly this: 

const mano = risultato.landmarks[0];
if (!mano) return;          // no hand in this frame: skip drawing

// or, in one line:
const polso = risultato.landmarks[0]?.[0];
console.log(polso?.x ?? "nessuna mano");

And it is the practical answer to what was said in lesson 6: types disappear before execution, so they do not protect you while the program runs. You have to write the check yourself.

Typical mistakes in class

Theory

Classes: an object that carries its own functions

In lesson 4 you learned objects: boxes with values inside. A class is the same idea, with one thing more: inside it there are also the functions that work on those values.

Look at today's problem. To damp the jitter you need to remember the last five values of a coordinate. With what you know so far: 

let ultimiValori: number[] = [];

function aggiungi(valore: number): void {
  ultimiValori.push(valore);
  if (ultimiValori.length > 5) ultimiValori.shift();
}

It works… for one coordinate. But the coordinates are 21 points × 3 axes = 63, and each one needs its own memory. With loose variables you would need 63 arrays and 63 functions. With a class, you write one and create 63. 

class MediaMobile {
  private valori: number[] = [];      // field: the memory of THIS object
  private readonly quanti: number;    // how many values to keep

  constructor(quanti = 5) {           // runs when the object is born
    this.quanti = quanti;
  }

  aggiungi(valore: number): void {    // method: a function of the object
    this.valori.push(valore);
    if (this.valori.length > this.quanti) this.valori.shift();
  }

  valore(): number {
    let somma = 0;
    for (const v of this.valori) somma += v;
    return somma / this.valori.length;
  }
}
const x = new MediaMobile(5);
const y = new MediaMobile(5);   // separate memory: two objects, two histories

x.aggiungi(0.42);
x.aggiungi(0.44);
console.log(x.valore());        // 0.43

That is all the vocabulary, and it is five words:

  • class — the mould: it says what an object of that type is made of and what it can do;
  • new — build an object from that mould;
  • constructor — what has to be done at birth;
  • field — a value the object keeps (valori, quanti);
  • method — a function the object can run (aggiungi, valore).

this means «this object here, not the other 62». And private means «not to be touched from outside»: whoever uses a MediaMobile calls aggiungi and valore, and does not even need to know there is an array inside. If tomorrow you change how the average is computed, no other file notices.

When you need a class and when you do not A class is needed when a piece of the program has to remember something between one call and the next, and there are several independent copies of it: the filter of each coordinate, the recognizer, the 3D scene. For a calculation that remembers nothing — aPixel, distanza — a function is simpler and perfectly fine. The real project has four classes in all: no more.

The interface state

Look at your lesson 8 page and count: the «Accendi» (turn on) button, the «Spegni» (turn off) one, the message, the error box, the fps counter. Five things that must be consistent with each other. If you switch them on and off one by one, scattered through the code, sooner or later you reach an absurd screen — «Camera off» written while the light is on, the «Starting…» button that stays there forever after an error.

The solution is to say first of all which states exist. It is a union type, like the ones in lesson 2: 

type Stato = "spenta" | "avvio" | "accesa" | "errore";

Four words, and no others: if you write "acesa", the compiler stops you straight away. Then a single function decides how each state looks: 

function setState(stato: Stato, messaggio: string): void {
  etichettaStato.textContent = messaggio;
  bottoneAccendi.disabled = stato === "avvio" || stato === "accesa";
  bottoneSpegni.disabled = stato !== "accesa";
  riquadroErrore.hidden = stato !== "errore";
  document.body.dataset.stato = stato;   // useful to the CSS and to whoever reads the page
}

From then on, in all the rest of the program, no button is touched any more: you call setState("avvio", "Carico il modello…") and that is it. The advantage is not writing fewer lines: it is that impossible states become impossible, instead of lying in wait.

Why the points jitter

Hold your hand still, really still. The points on screen keep dancing by a few pixels. It is not your fault and it is not a bug: the model analyses each frame on its own, and each frame is slightly different from the previous one — sensor noise, a little change in light. Small differences in, small differences out. Thirty times a second, and the eye reads them as a vibration.

The simplest idea to remove it is one you already know from school marks: instead of the current value, the average of the last five. The little jumps up and down cancel out and the hand calms down. 

// no filter                         average over 5
// 0.412 0.418 0.409 0.421 0.414     0.415 0.415 0.416 0.415 0.416

But there is a price, and it must be well understood because it is the heart of the lesson. If you move your hand suddenly, the average still contains four old values: the hand on screen arrives late, as if it were crawling behind yours. The stronger the filter, the slower it is. With 5 values the delay is barely noticeable; with 20 the hand seems to be in treacle. Try both: it is exercise 9.2.

How the real project does it (and why we do not write it today) The site uses the One Euro filter, which solves the trade-off instead of putting up with it: it measures how fast the point is moving and changes strength by itself — it filters a lot when the hand is still (no vibration), almost nothing when the hand is racing (no delay). It is about fifteen lines of maths, hand-written in the file filter.ts. Today you write the moving average because it lets you understand the problem with what you already know; if you want to look at the grown-up version you will find the file, commented in Italian, in the site's code.

Confirmation over several frames

There is a second, sneakier defect. Every now and then — one frame in fifty, when the light changes or something passes through the frame — the model «sees» a hand that does not exist. It lasts a single frame, but on screen it is an annoying flash.

The remedy costs three lines: do not trust the first time. You count for how many consecutive frames the hand has been present, and draw only from three onwards. 

let consecutivi = 0;
const CONFERME = 3;

if (risultato.landmarks.length > 0) consecutivi++;
else consecutivi = 0;

if (consecutivi >= CONFERME) {
  // only now is the hand drawn
}

Cost: a tenth of a second of delay when it appears, which nobody notices. Gain: the ghost hands disappear. It is the same reasoning as the filter — you pay a little delay to buy stability — and it is one of the most common choices in the whole trade.

let precedenti: Punto[] | null = null;
let sommaMovimento = 0;

/** Average displacement of the 21 points relative to the previous frame (in 0…1 units). */
function misuraTremolio(punti: Punto[]): void {
  if (precedenti && precedenti.length === punti.length) {
    let somma = 0;
    for (let i = 0; i < punti.length; i++) {
      const dx = punti[i].x - precedenti[i].x;
      const dy = punti[i].y - precedenti[i].y;
      somma += Math.sqrt(dx * dx + dy * dy);
    }
    sommaMovimento += somma / punti.length;
    misure++;
  }
  // copy of the values, not of the references: we need them as they were now
  precedenti = punti.map((p) => ({ x: p.x, y: p.y, z: p.z }));
}

  etichettaTremolio.textContent = `tremolio: ${(sommaMovimento / misure).toFixed(5)}`;
  sommaMovimento = 0;
  misure = 0;
}

Typical mistakes in class

  • Forgotten this: inside a method someone writes valori.push(...) instead of this.valori.push(...). The compiler says «Cannot find name 'valori'»: the field exists only through this.
  • Forgotten new: const f = FiltroMano(); builds nothing. You need new FiltroMano().
  • A single filter for all the points: the hand crumples towards a single point, and it is a memorable sight. You need 63 independent filters, one per coordinate.
  • Filter never thrown away: the hand coming back into the frame crawls in from where it left.
  • The hand «in treacle»: window too long. Bring it back to 5 and look again.
  • precedenti = punti instead of the copy: you save a reference to the array, not the values; at the next comparison the differences all come out zero and the measured jitter is 0.00000. It looks like a resounding success and it is not.
  • Two setState calls in a row with contradictory messages: the last one wins, and it is often the wrong one. One path, one state.

Theory

Three.js: scene, camera, lights, mesh

The browser can draw in three dimensions, but the interface it offers (WebGL) is ferociously awkward: matrices, programs for the graphics card, buffers of numbers. Three.js is the library that steps in between and talks the way people talk in a theatre. Four words and you have understood everything you need today:

  • scene (Scene) — the stage: the list of things that exist;
  • camera (PerspectiveCamera) — where you look from, and with what field of view: distant things get smaller, as in reality;
  • lights — without them, everything is black. An ambient light that brightens everywhere, a directional one that gives volume;
  • mesh (Mesh) — an object: a geometry (the shape: a sphere, a cylinder) plus a material (the colour, how shiny it is).
const sfera = new THREE.Mesh(
  new THREE.SphereGeometry(1, 20, 14),                    // shape
  new THREE.MeshStandardMaterial({ color: 0x38bdf8 }),    // appearance
);
sfera.position.set(0, 0, 0);
scena.add(sfera);

And then, at every frame, a single line: renderer.render(scena, camera). Three.js looks at where the objects are at that moment and draws the picture.

The idea that makes the difference Objects are created only once, at the start; at every frame they are moved. Creating and throwing away 21 spheres sixty times a second would keep the garbage collector working nonstop, and the hand would stutter. It applies to the 3D scene as to anything that runs at frame rate.

From 21 points to 21 spheres

Here is all the maths of the lesson, and it is three lines. The points coming from the webcam live in a world like this: x and y between 0 and 1, origin in the top-left corner, y growing downwards as in all images. The 3D world instead has its origin in the centre and the y growing upwards, as at school. 

function nelloSpazio(p: Punto) {
  const larghezza = 6;    // how wide the video rectangle is in the 3D world
  const altezza = 4.5;
  return {
    x: (0.5 - p.x) * larghezza,       // centre AND mirror
    y: (0.5 - p.y) * altezza,         // centre AND flip
    z: -p.z * larghezza * 1.6,        // depth, a little exaggerated
  };
}

Look at what that 0.5 - x does, because it does two jobs in one subtraction:

  • it moves the origin from the corner to the centre: the point at the centre of the image (0.5) becomes 0, that is the centre of the scene;
  • it reverses the direction of the axis. On y it takes you from the «y down» of images to the «y up» of 3D graphics. On x it is the mirror effect: move your hand to the right and the hand on screen goes to the right, as in front of a mirror. Without it, it feels like watching someone else, and it is strangely unpleasant.

The z has its sign flipped (MediaPipe's depth is negative towards the camera, in 3D the observer is on the positive side) and is multiplied by 1.6: the depth estimated from a single camera is small, and without some gain bringing your hand closer would hardly be noticed. The value is chosen by eye — any higher, and the hand starts to look deformed.

Putting a site online

So far you have worked on localhost, which is just your computer. «Putting online» means three things, and none of them is magic:

  1. Building: npm run build. The command checks the types, translates the TypeScript into JavaScript, joins the files, shortens them and writes everything into the dist/ folder. Inside there is a normal site — pages, scripts, images — that no longer needs either Node or Vite.
  2. A computer that is always on to serve those files to whoever asks for them, and a name (a domain) pointing to that computer.
  3. HTTPS, and here there is no choice: without a certificate, as you saw in lesson 7, the webcam does not turn on. Your project online on http:// would be a dead page.

The site you are looking at, for instance, runs on a small rented computer: one program serves the dist/ folder, another (Caddy) takes care of the domain and gets the HTTPS certificate by itself. Before publishing, a script checks that nothing strange has appeared in the built files and that all the pages are there; if a check fails, publishing stops and yesterday's version, which worked, stays online.

Nobody has to publish today Putting a site online requires an address, often a credit card and a few choices that should not be rushed on the last day of the course. Exercise 10.4 stops at npm run build and at looking at what is inside dist/: that is the part that counts. If you want to go further at home, you will find the simplest routes in the final list.

A few closing words: privacy and CSP

Your project handles images of people. It is the most sensitive data there is, and you handled it the right way almost without noticing: the images do not leave the browser, because there is nowhere to send them; the camera turns on only on click; it turns off when you switch tab. It is not by chance, it is a design choice — and the rule underneath it applies well beyond this course: the data you do not collect is the only data you cannot lose.

There is also a way not to just promise it. A site can declare to the browser what it is allowed to do — it is the Content Security Policy. The hand site declares, among other things, that the page may talk only to its own domain. From then on it is no longer the programmer who guarantees that the images are not sent to someone: it is the browser that refuses to send them, even if the code tried. The whole difference between a promise and a guarantee lies there.

In the real project this rule had an interesting side effect: it blocked a call nobody had written. It was the recognition library, which every minute sent some usage data to its servers — no images, but still a call to a stranger, and with no way to switch it off. It has been disabled. Without the CSP, nobody would ever have noticed.

import * as THREE from "three";
import type { Punto } from "./disegna";

const tela3d = document.getElementById("scena") as HTMLCanvasElement;

const scena = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(35, 1, 0.1, 100);
camera.position.set(0, 0, 10);

const renderer = new THREE.WebGLRenderer({ canvas: tela3d, antialias: true, alpha: true });

function adatta(): void {
  const w = tela3d.clientWidth || window.innerWidth;
  const h = tela3d.clientHeight || window.innerHeight;
  renderer.setSize(w, h, false);
  camera.aspect = w / h;
  camera.updateProjectionMatrix();   // required after changing the proportions
}
window.addEventListener("resize", adatta);
adatta();

// Lights: an ambient one so nothing stays black, a directional one that gives volume.
scena.add(new THREE.HemisphereLight(0xdbeafe, 0x1e1b4b, 1.4));
const principale = new THREE.DirectionalLight(0xffffff, 2.2);
principale.position.set(3, 5, 8);
scena.add(principale);

// 21 spheres, created ONCE only: at every frame they are just moved.
const geometria = new THREE.SphereGeometry(1, 20, 14);
const materiale = new THREE.MeshStandardMaterial({ color: 0x38bdf8, roughness: 0.35 });
const sfere: THREE.Mesh[] = [];
for (let i = 0; i < 21; i++) {
  const s = new THREE.Mesh(geometria, materiale);
  s.position.set((i - 10) * 0.35, 0, 0);   // in a row, until a real hand arrives
  s.scale.setScalar(0.12);
  scena.add(s);
  sfere.push(s);
}

const LARGHEZZA = 6;
const ALTEZZA = 4.5;

/** Moves the 21 spheres onto the 21 points of the hand (MediaPipe 0…1 coordinates). */
export function mostraMano(punti: Punto[]): void {
  for (let i = 0; i < 21; i++) {
    const p = punti[i];
    sfere[i].position.set(
      (0.5 - p.x) * LARGHEZZA,
      (0.5 - p.y) * ALTEZZA,
      -p.z * LARGHEZZA * 1.6,
    );
  }
  mostra(true);
}

/** Shows or hides the whole hand. */
export function mostra(visibile: boolean): void {
  for (const s of sfere) s.visible = visibile;
}

/** One frame. To be called inside the loop in main.ts. */
export function disegna(): void {
  renderer.render(scena, camera);
}

In dist/ you find index.html and an assets/ folder with oddly named files like index-a1b2c3d4.js. Those letters are the content fingerprint: if you change a line of code, the name changes, and browsers that had the old version in memory are forced to download the new one. The code inside is all on a few very long lines, with variable names cut down to one letter: it is minification, which makes for fewer bytes to download. Exercise 10.5 — Count the raised fingers challenge

The last challenge of the course, and you do it with what you know from lesson 3. A finger is raised if its tip is higher than the corresponding knuckle — remember that a small y means up. Show how many fingers you see, from 0 to 4 (the thumb is a special case: it moves sideways, not up).

Solution 
/** Index, middle, ring, little finger: tip and knuckle of each. */
const DITA = [
  { punta: 8, nocca: 5 },
  { punta: 12, nocca: 9 },
  { punta: 16, nocca: 13 },
  { punta: 20, nocca: 17 },
];

function contaDita(punti: Punto[]): number {
  let alzate = 0;
  for (const dito of DITA) {
    // smaller y = higher up in the image
    if (punti[dito.punta].y < punti[dito.nocca].y) alzate++;
  }
  return alzate;
}

It works with the hand upright and gets confused with the hand tilted, because it compares heights on the image and not relative to the palm. The serious version measures the distances from the wrist (distanza(punta, polso) > distanza(nocca, polso)) and is robust to rotations: it is a great first project to do at home. For the thumb, you look at the horizontal distance from the index knuckle.

Typical mistakes in class

  • Black screen: the lights are missing, or the canvas has no size in the CSS, or disegna() is never called. Check them in that order.
  • The hand is upside down: the 0.5 - on the y is missing, or it has become p.y - 0.5.
  • The hand moves the wrong way: the mirror on the x is missing. It is the same reasoning as the y, but for a different reason — here it is the user's comfort, there it is a conversion between two coordinate systems.
  • The hand is huge or invisible: it was given points in pixels instead of between 0 and 1.
  • Everything stutters: new objects are being created inside the loop. The spheres are created once, then moved.
  • npm run build fails while npm run dev worked: it is tsc checking the types for real. The errors are real and must be fixed; during development they were only ignored squiggles.

Quick check (5 questions)

Questions and answers
  1. What are the four ingredients of a Three.js scene? → Scene, camera, lights and mesh (geometry + material).
  2. What are the two jobs of (0.5 - x)? → It moves the origin to the centre and reverses the direction of the axis: on x it is the mirror effect, on y the conversion between «y down» and «y up».
  3. Why are the 21 spheres created outside the loop? → Because creating and destroying them at every frame would keep the garbage collector busy and cause stutters.
  4. What does npm run build produce? → The dist/ folder: a static site already translated into JavaScript, which no longer needs either Node or Vite.
  5. Why must a site with the webcam be on HTTPS? → Because outside a secure context the browser does not give access to the camera: the page would not work.

How to assess

With beginners, assessing only «the program works» rewards those who had already seen some code and penalizes those who start from zero and are really learning. The weights below take the journey into account, not only the result on the last day.

Classroom rules: webcam, privacy, tired people

  • You film only your own hand. No filming classmates, no other people's screens. It is a rule of good manners before it is a rule of law.
  • Whoever does not want to appear does not have to. A hand is enough for the frame, but if someone is uncomfortable they can work with a fake video (a clip recorded beforehand by the teacher, used instead of the camera) or in a pair with someone who turns on their own.
  • Nothing leaves the computer. It must be said explicitly and shown: in the whole project there is not a single line that sends images anywhere. It is also a good opportunity to talk about what apps that ask for the camera do instead.
  • The lights go off. At the end of the lesson, everyone closes the tab or presses «turn off camera»: it is part of the exercise, not a detail.

If someone falls behind (it will happen)

In a class of beginners, after lesson 3 the gap between the fastest and the slowest is already large. Three measures that work better than «catch up at home»:

  • Every lesson restarts from a restore point. The teacher keeps the complete code of the previous lesson ready: whoever got lost copies it and starts again from there, without dragging the delay along for twenty hours.
  • Exercises are labelled. basic for everyone, intermediate for most, challenge for those who finish early — so the fast ones have something to do and the slow ones do not feel guilty for not finishing.
  • Rotating pairs. From lesson 6 you work in twos at a single computer, swapping at the keyboard every 15 minutes. The one watching explains, the one typing carries out: you learn more in both roles.
