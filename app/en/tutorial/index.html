0 What we build, and what you need to know

Before writing a line, let's get the result clear, and the chain of pieces that produces it. Once this chain is clear, every chapter that follows is just "now let's make this piece work".

The result

A web page. You reach it with an address, press a button, and the browser asks for permission to use the camera. From then on you move your hand in front of the webcam and a stylized hand appears on the screen — spheres at the joints, sticks for the bones, a translucent palm — that follows yours, fingers included. At the bottom, the name of the gesture appears when it recognizes one: fist, thumb up, victory.

No installation for the viewer, no account, no server processing anything. The server does one thing only: deliver files. Everything else happens inside the browser.

The chain, in five links

# Link What goes in What comes out
1 Webcam the user's permission a video stream inside a <video> element
2 Recognizer a frame 21 landmarks for each hand, plus the name of the gesture
3 Filter 21 jittery landmarks 21 stable landmarks, with no noticeable delay
4 3D scene 21 landmarks spheres and cylinders placed and rotated
5 Loop the screen's heartbeat repeats steps 1-4 sixty times a second
Why the order matters

Each link has one job only and knows nothing about the others. The recognizer does not know a 3D scene exists, the 3D scene does not know the landmarks come from a webcam. That is why, in chapter 10, replacing "hand" with "whole body" will take half an hour and not a rewrite: only one link changes.

What you need to know already

  • Basic JavaScript: functions, const, objects, arrays, async/await. If you know what a Promise does, you are fine.
  • A little HTML and CSS: knowing that a <button> exists and that you can look it up by id.
  • The terminal: moving into a folder and running npm.

You need to know nothing about artificial intelligence, WebGL, rotation matrices or servers. The three least obvious things — the maths of the filter, the rotation of the cylinders and the configuration of the reverse proxy — I explain line by line when they come up.

What you need installed

What Version Why
Node.js 20 or later runs the development tools (Vite) and, at the end, the small server that publishes the site. It includes npm.
An editor any VS Code has the advantage of understanding TypeScript on its own and flagging errors while you type.
A recent browser Chrome, Edge, Firefox, Safari 16+ you need WebAssembly (for the model) and WebGL (for 3D). They have all had them for years.
A webcam — the laptop's built-in one is fine. In chapter 8 we will see how to work without one, with a fake camera.

Check that you have Node:

node --version
# v20.x o superiore. Se il comando non esiste: nodejs.org
Try it

Before reading on, open the Mano page of this site and turn on the camera. You will want the result in your head while you build the pieces: it is much easier to understand why an anti-jitter filter is needed once you have seen the hand still and stable.

1 Setting up the project

Ten minutes of scaffolding, and then you never think about it again.

  • package.json
  • vite.config.ts
  • index.html
  • src/main.ts

Creating the skeleton

# Crea un progetto Vite con TypeScript, senza framework
npm create vite@latest mano -- --template vanilla-ts

cd mano
npm install
npm run dev
# → il terminale stampa: Local: http://localhost:5173/

Open that address: there is a sample page. From now on every file you save reloads in the browser in under a second.

Why Vite, and why "vanilla"

Vite does two jobs. In development it serves the files to the browser without rebuilding the whole project at every save: you edit, save, see. In production it builds a static, minified site, with file names signed by their content (index-a1b2c3.js): if the content changes the name changes, so they can be cached forever without ever serving an old version.

No React, Vue or Svelte. The interface of this application is made of nine elements that change state all together, in a single place in the code. A framework would add a package, a build step and one more mental model to save twenty lines. The same goes for the CSS: no Tailwind, two hundred lines written by hand.

TypeScript, though, yes. This code is full of coordinates, indices and arrays of 21 elements. With types, a typo becomes a compile error instead of a crooked hand on the screen that you cannot explain.

Why five files and not one

It is not fussiness: camera.ts is the part that touches the most sensitive data (the images of a person). Keeping it alone in thirty lines means that anyone, in ten seconds, can check that there is no fetch, no MediaRecorder, no saving in there. In a thousand-line file the same check is an act of faith.

2 Turning on the webcam

Thirty lines, and almost all of them handle the cases where something goes wrong. That is normal: the webcam is someone else's hardware, and it can say no in five different ways.

  • src/camera.ts

The line that matters

const stream = await navigator.mediaDevices.getUserMedia({ video: true, audio: false });
video.srcObject = stream;
await video.play();

That's it: you ask for a stream, attach it to a <video> element, and play it. The rest of the chapter is about the four things that can go wrong.

The secure context: HTTPS or localhost

Browsers give access to the camera only in a "secure context": a page served over https://, or from localhost. On any plain http://, navigator.mediaDevices simply does not exist, and your code fails with an obscure Cannot read properties of undefined.

Practical consequence

In development everything works, because npm run dev serves the page on localhost. The day you publish it on a bare IP address or on a domain without a certificate, the camera simply does not start. That is why this project needed a real domain from day one: we deal with it in chapter 7.

Constraints: what to ask the camera for

Why ideal and not exact

With exact, a webcam that does not do exactly 640×480 makes the request fail with OverconstrainedError. With ideal the browser picks the closest format it has. Practically always what you want.

And why 640×480 exactly? Because the recognizer of chapter 3 does not get more accurate with bigger images — it resizes them internally anyway — but it gets slower. Asking for Full HD here only heats up the processor.

audio: false is not a formality: if you ask for audio, the browser asks the user for permission for the microphone too, and the matching indicator light turns on. Do not ask for what you do not need.

Errors, translated into useful sentences

When getUserMedia fails, it throws a DOMException with a standard name. Showing that name to the user is useless; translating it takes five lines.

Error What really happened What the user can do
NotAllowedError they pressed "Block", or permission was already denied for this site re-enable it from the padlock icon in the address bar
NotFoundError no camera connected connect one
NotReadableError the webcam is already in use by Zoom, Teams, another tab… close the other application
OverconstrainedError the requested constraints are impossible for that camera nothing: it is your fault, use ideal
Why a CameraError class of its own

Because higher up, in main.ts, you want to tell apart two very different situations: an expected problem, with a ready-made message to show, and a bug in your code, for which it is better to show the technical text. One line: e instanceof CameraError ? e.message : `Errore durante l'avvio: …`.

A detail that bites: the dimensions arrive later

Without this wait you end up, now and then and only on some machines, with a 3D scene with NaN proportions. The classic bug that does not reproduce on your computer.

Turning off the camera for real

Mistake number one

Stopping the <video> element does not turn off the camera. The stream stays open and the laptop's green light stays on: from the point of view of whoever uses the site, you are still filming them. Every single track must be stopped.

3 Recognizing the hand

This is where the magic happens, and it is twenty lines. Google has already done all the hard work: we load a model and pass it frames.

  • src/tracker.ts
  • scripts/prepare-assets.mjs

The library

npm install @mediapipe/tasks-vision@1.0.1
Why MediaPipe, and why the version is pinned exactly

MediaPipe Tasks Vision is the library Google uses to run its own vision models inside the browser, compiled to WebAssembly. A single model gives both the 21 hand landmarks and the name of eight gestures. The alternatives — TensorFlow.js with handpose, or an ONNX model on onnxruntime-web — are slower or require you to write the gesture recognition by hand.

1.0.1 and not ^1.0.1: the runtime and the model file must match, and (we will see this in chapter 7) a security patch relies on an exact string in the compiled file. An automatic update would break the build — and that is exactly what we want: better a build that stops than a behaviour that changes silently.

The 21 landmarks

For each hand it sees, the model returns an array of 21 objects. They are always in the same order, and it is that order that gives meaning to the numbers:

Indices Part
0 wrist
1 · 2 · 3 · 4 thumb, from base to tip
5 · 6 · 7 · 8 index (5 = knuckle, 8 = tip)
9 · 10 · 11 · 12 middle
13 · 14 · 15 · 16 ring
17 · 18 · 19 · 20 little finger

Each landmark has three numbers:

Meaning Range
x horizontal position on the image 0 (left edge) … 1 (right edge)
y vertical position 0 (top) … 1 (bottom)
z depth relative to the wrist same scale as x; negative = closer to the camera

Two important things. First: the coordinates are normalized, that is, they are not pixels. If the webcam changes resolution, the numbers do not change — great news for the code that uses them. Second: z is the least reliable of the three, because it is estimated from a single camera. It is enough to tell that a finger points forward; do not trust it to measure distances.

Why y grows downwards

Because it is the convention of images: the origin is the top-left corner, as for an HTML canvas. In 3D graphics, instead, y grows upwards. Between the two worlds there is a conversion, and we will do it in chapter 5. Make a note of it: it is the source of half the "the hand is upside down" bugs.

Loading the model

FilesetResolver is the piece that throws everyone the first time: it does not load the model, it loads the engine. It is the WebAssembly runtime that can run MediaPipe's neural networks; the model (the .task file) is the "content" that engine runs. They are two separate downloads: about 11 MB the first, about 8 MB the second, and then they stay in the browser cache.

Why runningMode: "VIDEO" changes everything

In IMAGE mode every frame is analysed from scratch: the model looks for the hand in the whole image, every time. In VIDEO mode the model knows that the frames are consecutive and tracks the hand from one frame to the next, looking for it only where it expects to find it. Result: faster, more stable, fewer "jumps".

The 0.5 thresholds are the ones Google recommends. Raising them reduces false positives, but the hand gets "lost" more often — and a hand that disappears and reappears is much more annoying than a slightly imprecise hand.

Analysing a frame

Note something counter-intuitive: recognizeForVideo is synchronous. It does not return a Promise: it does the computation at once and blocks the main thread for its duration — a few milliseconds with the graphics card. That is why, in chapter 4, you will not find any await inside the frame loop.

The result you get:

Open_Palm🖐️ Open hand
Pointing_Up☝️ Index up
Thumb_Down👎 Thumb down

Graphics card or processor: the automatic fallback

delegate: "GPU" tells MediaPipe to do the maths on the graphics card. As a rule it is the right choice. On some configurations, though, the opposite happens — and spectacularly: inside a browser without a real graphics card (for example in an automated test on a server) the emulated GPU can take 3-5 seconds per frame, while the CPU does 4-6 per second.

The try/catch covers the "there is no WebGL" case. It does not cover the "WebGL is there but is extremely slow" case: that one has to be measured. We keep the average duration of a detection…

…and, if the average breaks the threshold, we recreate the recognizer on the CPU:

detections < 8 avoids judging on the first frames, which are always slow (shader compilation, cold caches). The 150 ms threshold means fewer than 7 frames per second: below that figure the application is already unusable, so it is worth risking a switch.

Runtime and model: from your site, not from a CDN

The official MediaPipe documentation has you load the wasm and the model from a CDN, with an address containing @latest. For an example that is perfectly fine. For a real site there are two good reasons not to:

  1. Privacy. In chapter 7 we will set a rule that lets the page contact only its own domain. It is that rule that makes the sentence "the images do not leave your browser" verifiable. If the model came from a CDN, the rule would have to be widened.
  2. Stability. @latest means "today's version". The day a new one comes out, your site changes on its own, perhaps breaking, without you having touched anything.

The solution is a script that runs before every build: it copies the runtime from node_modules (so the same version as the package) and downloads the model verifying its checksum.

Everything in public/ ends up in the build as it is, without going through the bundler and without its name changing. That is exactly what you need for files that must be reachable at a fixed address, like /mediapipe/gesture_recognizer.task.

4 The frame loop

Twelve lines that decide whether the application is smooth or heats up the laptop.

  • src/main.ts

Three details that look trivial and are not

requestAnimationFrame and not setInterval

The browser calls loop just before redrawing the screen. Three consequences, all good:

  • drawing is synchronized with the monitor: no images "torn" halfway through an update;
  • if the monitor runs at 120 Hz the loop follows on its own, without you changing a constant;
  • if the tab goes into the background the browser pauses the loop, instead of letting it drain the battery in secret. setInterval would keep running, piling up frames nobody is watching.

Skipping the frame already analysed

The screen refreshes 60 times a second, the webcam produces 30 frames a second: half the turns of the loop would find the very same frame. Analysing it twice is wasted work — and anyway MediaPipe, in video mode, refuses two analyses with the same timestamp (chapter 3).

The trick is video.currentTime: it changes only when a new frame arrives. Comparing it with the previous value costs one comparison and halves the work.

Drawing stays outside the if

Recognition runs at 30 Hz, drawing at 60. If you put scene.render() inside the if, the fades of hands coming in and going out would be jerky. Outside, the scene keeps animating even when nothing new arrives from the camera.

Summary of the rates

~60 times a second: the loop runs and the 3D scene is redrawn.
~30 times a second: a new frame arrives and the model works.
once a second: the fps counter is updated.

Counting frames (the right ones)

Note where this block sits: inside the if. It counts the analysed frames, not the drawn ones. The number of draws would always be 60 and would tell you nothing; the number of analyses tells you whether the application "keeps up" with the hand. It is the only metric that really matters, and it is also the first place to look when something is slow.

Start and stop

The two-loops bug

cancelAnimationFrame(rafId) before loop() looks useless. It is not: a double click on the start button is enough, or a restart while the first start() is still waiting for the camera, and you end up with two loops running in parallel. The symptom is bizarre — the application uses twice the resources and the hand stutters — and the cause is hard to imagine by looking at the drawing code.

The recognizer, note, is not closed: it stays in memory, ready for an instant restart. It is closed only when you leave the page. The webcam, instead, turns off at once: it is the camera, not a model.

A single place decides what you see

Why this boring function is worth writing

Because it avoids the most common class of bugs in an interface: two elements telling different states. The button says "Turn on camera" while the label says "● Camera on", because one of the two was updated in one code branch and the other was not. With a single place that decides everything, that situation is impossible by construction. It is also the reason this application does not need React.

Moving to 3D: Three.js

npm install three@0.186.0
npm install --save-dev @types/three@0.186.0   # stessa versione, o descrive funzioni che non esistono
Why Three.js and not "bare" WebGL

Direct WebGL means writing shaders, projection matrices and graphics context management: hundreds of lines before you even see a sphere. Three.js is the standard library for this, it has no dependencies of its own, and the whole scene of this project fits in a single three-hundred-line file, comments included. In exchange it weighs about half a megabyte compressed: for a 3D application it is the right price.

The minimal scene

Why three lights and not one

With a single directional light, the shaded side of every sphere turns black and the hand looks cut out. The hemisphere light fills the shadows with a colour instead of black; the key light gives volume; the grazing one from behind traces a bright rim that separates the figure from the dark background. It is the classic three-point scheme of photography, and in 3D it works the same.

Converting the coordinates

MediaPipe speaks in image coordinates (0…1, origin at the top left, y pointing down). Three.js speaks in world coordinates (origin at the centre, y pointing up, arbitrary units). The bridge between the two worlds is this function:

The 0.5 - does two jobs in one subtraction. It moves the origin from the corner of the image to the centre, and it flips the direction of the axis:

  • on x the flip is the mirror effect: you move your hand to the right, the one on the screen goes right, as in front of a mirror. Without it, the movement would be reversed and the experience immediately becomes unpleasant;
  • on y it is the conversion between the convention of images and that of 3D graphics. If you skip it, the hand is upside down.

DEPTH_GAIN = 1.6 amplifies depth: without it, moving the hand closer to the camera would barely be noticeable, because MediaPipe's z is small compared with the other two coordinates. The value is chosen by eye — above 2 the hand starts to look deformed.

One object per joint, one per bone

The idea that holds the whole file together

The objects are created only once in the constructor; on every frame they are only moved. Creating and destroying 40 objects 60 times a second would keep the garbage collector constantly busy, and you would see it: stutters at irregular intervals, the kind you cannot relate to anything.

MeshStandardMaterial is a "physical" material: it reacts to lights, so the spheres look like volumes and not flat circles. The fingertips use a material that emits its own light, so they stay readable even when they end up in shadow.

How to place a bone

This is the only piece of real maths in the drawing. You have a cylinder 1 high and 1 wide, centred at the origin and oriented along the Y axis. You have to take it from a point A to a point B. Three operations:

setFromUnitVectors is the function that saves you from learning quaternions: given two unit vectors, it computes the rotation that takes the first onto the second. You only have to remember that the two vectors must be normalized, that is of length 1 — and that is exactly what divideScalar(len) does.

Sizes proportional to the hand

If the radii were constant, a distant hand would look made of balloons and a close one of pins. By tying them to a distance inside the hand, the figure stays believable at any distance from the camera, for free.

The palm

Two lines that save hours: frustumCulled and needsUpdate

frustumCulled = false. To avoid drawing objects out of frame, Three.js checks a bounding volume computed only once. If the vertices move, that volume becomes wrong and the palm disappears intermittently. Confusing symptom: it looks like a transparency problem.

pos.needsUpdate = true. Without it, Three.js does not resend the data to the graphics card: the palm stays frozen in the position of the first frame while the fingers move. Another classic.

The fades

Without a fade, every time the model loses the hand for one frame the figure disappears and reappears abruptly. With a tenth of a second of transition, the same loss becomes invisible.

Adapting to the window

If you forget updateProjectionMatrix() the scene keeps being drawn with the old proportions: the hand looks squashed or stretched after every resize of the window. It is the first place to look when "the 3D is crooked".

6 Making it look smooth

At this point everything works and it looks badly made. Three problems, three cures — and the third is the most elegant in the whole project.

  • src/filter.ts
  • src/main.ts

Problem 1: the landmarks jitter

Hold your hand perfectly still and watch the dots in the preview: they dance. It is not your fault, it is the model: every frame is a slightly different image (sensor noise, compression, lighting that changes a little), and the neural network answers with slightly different numbers. On the screen, a hand that vibrates.

The obvious cure, and why it is not enough

Averaging with the previous frames. It removes the jitter, but introduces lag: move your hand suddenly and the one on the screen arrives later, as if it were in treacle. It is the classic trade-off between stability and responsiveness, and with a fixed-strength filter you cannot win: if you filter enough to stop the jitter, you filter too much to follow a movement.

The One Euro filter, explained in words

The idea (Casiez, Roussel, Vogel — CHI 2012) is shamelessly simple: change the strength of the filter according to how much the landmark is moving.

  • landmark almost still → filter a lot → no vibration;
  • fast landmark → filter little → no noticeable lag.

It works because the two defects never show up together. When the hand is still, the lag cannot be seen (nothing is moving for it to lag behind). When the hand races, the jitter cannot be seen (it is hidden by the movement). The filter exploits exactly this: it always corrects the defect that is visible at that moment.

The name comes from the title of the paper: a filter that "costs one euro", that is, very simple.

The code, in three pieces

Three parameters, three knobs:

Parameter Value What it controls
minCutoff 1.2 how much to filter when the hand is still: lower = more stable but slower
beta 8 how much to "open" the filter with speed: higher = follows fast movements better
dCutoff 1 filter on the speed estimate, so that it does not jump around
How to tune them

By eye, in this order. First set beta to 0 and lower minCutoff until the still hand is perfectly stable (it will be very slow in its movements). Then raise beta until fast movements are immediate again. If the jitter comes back, you went too high.

Applying it to the 21 landmarks

One instance per hand, thrown away when the hand disappears

If you reuse the same LandmarkSmoother when the hand reappears, the filter "remembers" where it was before and the hand arrives crawling from the old position. A very strange effect to watch and very hard to blame on the filter.

Problem 2: the ghost hand

On sudden image changes, MediaPipe now and then "sees" for a single frame a second hand that is not there. In this project's tests it happened 2 times out of 117: on the screen it was an annoying pink flash.

The cure is to wait for a confirmation:

Cost: a tenth of a second of delay when the hand appears, which nobody notices. Benefit: zero ghost hands. Note the detail of the filter running even during the confirmation frames — it is free and makes the hand appear already steady.

Problem 3: right and left are swapped

How you notice a bug like this

Not by looking at it: looking at your own hand it is very easy to convince yourself it is right. You need an independent test. In this project it was a photo of a left hand taken from the MediaPipe tests, fed to the model: the library answered "Right". End of discussion.

In chapter 8 this check became one of the eight automated tests, precisely because it is a bug that is very easy to reintroduce without noticing.

One last subtlety: who uses the filtered landmarks

In the preview the dots sit on top of the webcam image: if they were filtered, you would see them slide relative to the real fingers, and it would look like a calibration error. In 3D there is nothing to compare them with, and the filter is pure gain.

7 Going online

You need HTTPS (otherwise the webcam does not start) and you need a rule that makes the sentence "the images do not leave your browser" verifiable, not just promised.

  • vite.config.ts
  • server.mjs
  • Caddyfile

The build

npm run build
# 1. prepare-assets.mjs → wasm e modello in public/mediapipe/
# 2. tsc                → controlla i tipi, non produce niente
# 3. vite build         → impacchetta, minifica e scrive in dist/
Why tsc in the middle, if it produces no files

Because Vite does not check types: it just strips them, which is why it is fast. Without that step, a type error would reach production and become a runtime error. Putting it in the build chain means that a build with type errors simply does not complete.

In dist/ you find the index.html, an assets/ folder with the content-signed files and the copy of public/. It is all static: any server can serve it.

An eighty-line static server

If you can let your reverse proxy read the folder directly, do it and skip this paragraph. In this project it was not possible: the proxy runs as a user that cannot enter the project folder, and copying the site elsewhere would have scattered pieces of the project outside its folder. So: a Node process that serves dist/ and listens only on the machine itself.

The type of the .wasm

If the server answers application/octet-stream for a .wasm file, the browser refuses to compile it on the fly and MediaPipe does not start. The error message talks about streaming compilation and never mentions the content-type: it is one of the most common lost quarter-hours in this kind of project.

The reverse proxy, with HTTPS

In front of the static server we put Caddy, which takes care of the certificate (it obtains and renews it on its own), compression and the security headers. The full chain: 

internet → Caddy (HTTPS, intestazioni) → 127.0.0.1:8791 → server.mjs → dist/

The CSP, directive by directive

Directive What it does
default-src 'none' start from a total ban, then reopen only what you need
script-src 'self' 'wasm-unsafe-eval' JavaScript only from your domain; the wasm permission is needed to compile the MediaPipe runtime and does not enable JavaScript eval()
style-src 'self' only your own stylesheets: no <style> in the page, no style="…"
img-src 'self' data: blob: your images, or images generated by the page itself
media-src 'self' blob: the webcam stream reaches the page as blob:: without this the preview stays black
connect-src 'self' the line that matters — see below
frame-ancestors 'none' nobody can frame your site inside theirs to steal clicks
Why connect-src 'self' is the real guarantee

Up to here, "the webcam images do not leave the browser" is a promise: you have read the code and found no fetch, and you trust it. But the site also contains hundreds of kilobytes of compiled library that nobody reads line by line.

connect-src 'self' changes the nature of the claim. It tells the browser: this page may make network requests only to its own domain. A fetch to any other address — written by you by mistake, hidden in a dependency, injected by an attack — is blocked by the browser and reported in the console. It is no longer the code that promises: it is the browser that refuses.

It is a promise anyone can check in thirty seconds, without reading your code: open the developer tools, Network tab, and check that nothing goes outside.

The hidden telemetry

And here is a real case where that rule earned its place. @mediapipe/tasks-vision creates inside every task a logger that every 60 seconds sends some usage metrics to a Google endpoint: task type, mode, timings, operating system. No images — but it is still a call to a third party, and the library offers no way to turn it off. We discovered it precisely because the CSP blocked it and the browser reported it in the console.

A fragile patch, on purpose

Replacing an exact string inside a minified file is fragile and we know it. But the fragility here is a feature: the day the library changes that string, the build fails with an explicit message and someone goes to look. The silent alternative — a try/catch that ignores the problem — would turn the telemetry back on without anyone ever knowing.

Automated checks before publishing

Publishing is a script that runs the build, then checks, and stops at the first failed check, leaving the previous, working version online: 

✓ nessuno <script> o style= scritto dentro le pagine di dist/
✓ nessun indirizzo esterno nei file prodotti
✓ nessuna traccia dell'endpoint di telemetria
✓ wasm e modello presenti e della dimensione attesa
✓ la configurazione del proxy è valida
✓ il servizio risponde dopo il riavvio

They are six grep and two curl. They are worth more than any mental reminder, because they never forget.

8 Testing without a webcam

The project lives on a server with no screen and no camera. And the most important thing to check is precisely "the camera turns on and the hand is tracked".

  • tests/e2e/run.mjs
  • tests/e2e/make-video.sh
Why not unit tests

The things that can break here are: camera permissions, loading the WebAssembly, the CSP, WebGL. None of these exists outside a real browser. Simulating them with mocks would give a test that passes while the site is broken — the worst of all possible worlds, because it also makes you feel safe.

Piece 1: a fake webcam

Chromium can use a video file instead of the camera. You just build an MJPEG clip with a moving hand — in this project four public photos from the MediaPipe tests (victory, thumb up, index up, fist) edited with ffmpeg so that the hand sways over the background — and pass it to the browser at startup: 

--use-fake-ui-for-media-stream            # concede il permesso senza mostrare il pop-up
--use-fake-device-for-media-stream       # usa una telecamera simulata…
--use-file-for-fake-video-capture=…/hands.mjpeg   # …alimentata dal filmato
--enable-unsafe-swiftshader              # WebGL via software: il server non ha scheda grafica

Piece 2: the same proxy as production

This way the CSP is the real one too: if a security rule breaks the site, you find out here and not on publishing day.

Piece 3: Playwright, and a back door

A test cannot "see" a 3D scene. So the page, and only when asked to, writes what it is seeing into data-* attributes:

Why it is off outside tests

Because it is still data about the hand of whoever uses the site, and any browser extension could read it from the page. A back door for tests should be opened only when needed, and the key is in the address: ?e2e.

What is worth checking

Eight checks. None is about "function X returns Y": all of them are about the application works. 

✓ la risposta ha la CSP di produzione
✓ la camera si accende e il modello si carica
✓ almeno 10 rilevazioni con la mano
✓ almeno 3 dei 4 gesti del video sono riconosciuti
✓ la mano del video (sinistra) è indicata come sinistra
✓ il movimento viene seguito (il polso si sposta di oltre 0,15)
✓ dopo «Spegni camera» lo stream è rilasciato
✓ nessuna richiesta verso altri domini, nessun errore in console
Check What it protects
the left hand is called left the flip of chapter 6, very easy to break without noticing
the wrist moves by more than 0.15 that the application tracks, not just recognizes: a bug in the frame loop would give a correct but motionless hand
the stream is released the webcam light that stays on after turning off
zero external requests the privacy promise, measured instead of declared

The test ends by printing E2E OK and leaves a screenshot on disk, to look at by eye: automation checks the numbers, the eye checks that you have not ended up with an upside-down purple hand.

This is not pessimism: these are the real problems met while building this application, with the symptom to recognize. Almost every odd line in the code comes from one of these.

Symptom Cause Cure
The right hand is called left MediaPipe assumes the image is already mirrored, as in a video call; the raw webcam frame is not realSide() that flips the label, and a test with a photo of a known hand (chapter 6)

The common thread

Look at how many of these bugs are not logic errors, but unstated assumptions that do not hold: "the image is mirrored", "the vertices do not move", "the GPU is faster", "the video dimensions are already available". It is the kind of problem you do not prevent by reading the code: you prevent it by trying it on a machine different from your own.

10 Where to go next

You have a pipeline that works: video → landmarks → filter → figure. Changing the central piece opens up a whole catalogue.

The other MediaPipe tasks

The same @mediapipe/tasks-vision library contains much more than the hand recognizer, and they all follow the identical shape: FilesetResolver, createFromOptions, …ForVideo(video, timestamp).

Task What it returns Idea
PoseLandmarker 33 body landmarks: head, shoulders, elbows, hips, knees, ankles a stick figure that imitates you. It is the second demo of this site: the Body page
FaceLandmarker 478 face landmarks, plus 52 "blendshapes" (smile, closed eye…) a mask that follows your expressions, or an avatar that copies you
ImageSegmenter a mask that separates the person from the background blurred or replaced background, as in video calls
ObjectDetector boxes and labels of the objects in frame count things, or make the scene react to an object
What really changes when moving to the whole body

One file: the one that talks to MediaPipe. The frame loop, the anti-jitter filter, the coordinate conversion and the scaffolding of the 3D scene stay identical — the filter becomes 33×3 instead of 21×3, and the connection table changes. That is exactly the advantage you buy by separating the modules in chapter 1: you do the hard work once.

Exercises, easiest first

  1. Change the colours. One constant in hand3d.ts. It helps you get comfortable without risk.
  2. Add a gesture of your own. Without training anything: look at the distances between the fingertips and the wrist. "All tips far from the palm and the thumb apart" is an open hand; "index tip very close to the thumb tip" is the OK gesture.
  3. Make the scene react. With a closed fist the hand turns red, with victory some particles appear. The value is already there, in result.gestures[i][0].categoryName.
  4. Measure the thumb-index distance and use it as a slider: raise and lower a value by pinching your fingers. It is the classic "pinch" without a touchscreen.
  5. Draw in the air. Trace a trail behind the index tip, and erase with the fist. You need a list of past points and a line geometry.
  6. Hand + body together. Two recognizers on the same frame. Watch out: it doubles the cost, and it is the moment when the fps counter of chapter 4 becomes your best friend.

A final tip

Do not build the whole chain before trying it. Get the webcam started and stop there. Then print to the console the number of hands seen, and stop there. Then draw the dots in 2D, and stop there. Every piece that works on its own is a piece you will not have to suspect when something goes wrong — and something will go wrong, because chapter 9 exists.
